RAG 部分

本周学习主题：RAG（检索增强生成）基础架构与实现流程

1.1 Overview：RAG 是什么？

本周首先了解了 RAG 的基本概念，即让大模型在回答问题前，先从外部知识库中检索相关内容，再结合检索结果生成答案。
RAG 的核心流程可以概括为：知识库 → 检索相关知识 → 提供给大模型 → 生成答案。

1.2 Indexing：索引构建

学习了如何把原始文档加工成适合检索的知识库。整体过程包括数据获取、文档预处理、文档分块、向量化以及存入向量数据库。

2.1 数据获取（Data Ingestion）

了解了 RAG 的第一步是获取知识来源，例如 PDF、Word、网页、数据库等。
数据质量会直接影响后续检索和生成效果，因此需要保证数据完整、准确。

2.2 文档预处理（Preprocessing）

学习了对原始文档进行清洗和整理，例如去除无意义内容、统一格式、处理特殊字符等。
预处理的目的主要是减少噪声，让后续分块和向量化更加有效。

2.3 文档分块（Chunking）

了解了长文档不能直接整体进行检索，需要切分成合适大小的文本块。
分块太大可能导致检索不够精准，太小又可能丢失上下文，因此需要根据实际内容选择合适的分块策略。

2.4 向量化（Embedding）

学习了 Embedding 的基本作用：把文本转换成计算机可以比较的向量。
语义相近的文本通常具有更接近的向量，从而可以通过向量相似度找到相关知识。

2.5 存储到向量数据库

将文本块及其对应的向量存入向量数据库，为后续检索做准备。
查询时可以根据问题向量快速找到与问题最相关的文本内容。

1.3 Retrieval：检索

Retrieval 是 RAG 中负责“找到相关知识”的部分。
主要学习了查询处理、向量检索、检索策略以及检索效果评价。

3.1 查询处理

用户提出的问题不一定适合直接进行检索，因此需要对查询进行一定处理。
目标是让查询能够更准确地匹配知识库中的相关内容。

3.2 向量检索

将用户问题转换成向量，然后与知识库中的文本向量进行相似度计算，找到最相关的内容。
这是 RAG 中比较核心的检索方式之一。

3.3 检索策略

了解到实际 RAG 系统不一定只依赖单一的向量检索，还可以结合关键词检索、混合检索、重排序等方式。
好的检索策略能够减少无关信息，提高最终回答的准确性。

3.4 检索效果评价指标

学习了需要通过指标判断“检索出来的内容到底有没有用”。
重点关注检索结果的相关性、准确性和召回能力，为后续优化 RAG 提供依据。

1.4 Generation：生成

Generation 负责利用检索到的知识生成最终答案。
基本流程是：构建 Prompt → 调用 LLM → 对答案进行后处理 → 评价生成效果。

4.1 提示词构建（Prompt Engineering）

学习了如何把用户问题和检索到的知识组织成合适的 Prompt。
Prompt 的重点是明确告诉模型任务、参考资料以及回答要求，减少模型脱离知识库自由发挥的情况。

4.2 调用 LLM 生成

将处理好的 Prompt 发送给大模型，由大模型结合检索到的知识生成最终回答。
这一环节重点理解了 RAG 与普通 LLM 对话的区别：RAG 会额外提供外部知识作为回答依据。

4.3 答案后处理

模型生成答案后，还可以进行格式整理、内容过滤以及引用信息处理。
目的主要是让最终结果更加清晰、可靠，也方便用户确认答案来源。

4.4 完整的 RAG 生成代码

将前面学习的内容串联起来，形成完整的 RAG 流程。
通过代码进一步理解 数据处理 → 向量化 → 检索 → Prompt → LLM 生成 各模块之间是如何配合的。

4.5 生成效果评价

最后学习了如何评价 RAG 最终生成的答案，而不仅仅是看答案是否“读起来合理”。
重点关注答案的准确性、相关性、完整性以及是否基于检索到的知识。

4.1 ReAct 框架

这周主要学习了 ReAct，简单理解就是让 Agent 先想一想，再去做事情，然后看看做的结果，再决定下一步怎么做。
比如遇到一个复杂问题，它不会一次性直接回答，而是可以不断地“思考 → 调工具 → 看结果 → 再思考”，直到把事情完成。

ReAct 的核心循环

对 ReAct 有了一个比较直观的认识，它其实就是一个不断循环的过程。
可以简单理解成：我现在要干什么 → 我应该怎么做 → 调用工具 → 得到结果 → 根据结果继续做。

完整的 ReAct 示例

通过完整案例进一步理解了 ReAct 是怎么工作的，不只是停留在概念上。
发现 Agent 和普通聊天机器人的区别比较明显，Agent 可以根据当前情况自己决定下一步做什么。

ReAct 的代码实现

结合代码看了一遍 ReAct 的实现，对 Agent 背后的基本结构有了更具体的认识。
简单来说，就是让大模型负责“想”，让工具负责“做”，然后把工具返回的结果继续交给大模型判断。

4.2 其他 Agent 工作模式

除了 ReAct，还了解了几种常见的 Agent 工作方式，比如 CoT、Plan-and-Execute、Self-Ask。
它们本质上都是在解决一个问题：面对比较复杂的任务，怎么让 Agent 一步一步把事情做好。

模式1：Chain of Thought（CoT）

CoT 可以简单理解成做事情之前先把思路理清楚，把一个复杂问题拆成几个小问题再解决。
这样比直接给出答案更容易处理复杂任务。

模式2：Plan-and-Execute

这种方式比较像先做计划，再按照计划执行。
比如让 Agent 完成一个大任务，它会先列出需要做的几个步骤，然后一步一步执行，而不是边想边做。

模式3：Self-Ask

Self-Ask 可以理解成自己不断提问题，再自己解决问题。
遇到一个复杂问题时，先把它拆成几个简单的问题，逐个解决，最后再把结果合起来。

4.3 理解 Agent 的三种视角

这部分主要是换不同角度去理解 Agent，而不是单纯记概念。
我目前觉得可以把 Agent 简单理解成：一个会自己干活的员工、一个不断循环的系统、一个大脑加上一堆工具。

视角1：把 Agent 看作“员工”

可以把 Agent 想象成一个员工，我们只需要告诉它目标是什么，它自己想办法完成。
大模型相当于员工的大脑，搜索、代码执行、数据库等就是它可以使用的工具。

视角2：把 Agent 看作“循环系统”

从这个角度看，Agent 并不是“一次思考就结束”，而是不断循环。
思考 → 行动 → 获取结果 → 再思考 → 再行动，直到任务完成。

视角3：把 Agent 看作“大脑 + 工具”

大模型本身更像一个“大脑”，但是光有大脑很多事情做不了，所以需要工具来帮它完成实际操作。
例如大模型负责判断和规划，搜索工具负责查资料，代码工具负责计算，数据库负责查数据。
