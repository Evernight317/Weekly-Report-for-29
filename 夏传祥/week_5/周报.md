## 二、核心学习内容

### 2.1 Day12 登录认证复习巩固

上一周学习登录认证时知识点比较密集，本周通过复习把整体脉络重新梳理了一遍：

- **会话跟踪技术演进**：Cookie + Session（服务端存储、依赖 Cookie、跨服共享难）→ JWT（无状态、服务端不存、适合分布式），理解了演进背后的动机。
- **JWT 令牌**：复习了 `jjwt` 的生成与解析、载荷设计（存入 id 与用户名）、过期时间与签名密钥的作用。
- **Filter 与 Interceptor 双层拦截**：重点对比了两者的定位差异——Filter 是 Servlet 级组件（先执行、作用所有请求、不受 Spring 管理），Interceptor 是 SpringMVC 级机制（可注入 Bean、可精确配置放行路径）。
- **结合苍穹外卖代码加深理解**：企业项目实际采用的是"Interceptor 校验 JWT + ThreadLocal 存取当前登录用户"的写法，与 Tlias 中"Filter 校验"的实现形成对比，直观感受到了两种方案的取舍。

### 2.2 Day13 事务管理进阶

- **Spring 声明式事务**：使用 `@Transactional` 注解声明事务边界，由 Spring 通过 AOP 在方法前后自动开启/提交/回滚事务，省去了手动 `BEGIN / COMMIT / ROLLBACK` 的样板代码。
- **rollbackFor 属性**：默认情况下事务**只对 RuntimeException（及 Error）回滚**，受检异常（如 IOException）不会触发回滚；需要回滚时需显式指定 `rollbackFor = Exception.class`。同时也踩到了"异常被 try-catch 吞掉导致事务不生效"的经典坑。
- **propagation 传播行为**：重点理解了 `REQUIRED`（默认，加入当前事务，没有则新建）与 `REQUIRES_NEW`（挂起当前事务、新开独立事务）在"日志记录类操作不应随主事务回滚"场景下的区别。
- **事务失效场景**：方法内部 `this` 自调用不经过代理、事务方法非 public、异常被捕获吞掉等，理解了"事务本质是 AOP 代理"后这些坑都能对上号。

### 2.3 Day13 AOP（面向切面编程）

- **核心概念**：切面（Aspect）、连接点（JoinPoint）、切入点（Pointcut）、通知（Advice）、目标对象、代理——先用一个"给方法加日志"的直观案例建立整体认知。
- **五种通知类型**：
    - `@Before` 前置通知：方法执行前
    - `@After` 后置通知：方法执行后（无论成败）
    - `@Around` 环绕通知：最强大，可手动控制方法执行、修改参数与返回值
    - `@AfterReturning` 返回后通知：正常返回后
    - `@AfterThrowing` 异常后通知：抛出异常后
- **通知顺序**：多个切面同时作用时，通过 `@Order(数字)` 控制执行顺序（数字越小优先级越高）。
- **切入点表达式**：
    - `execution()`：按方法签名匹配，如 `execution(* com.sky.service.*.*(..))`
    - `@annotation()`：按注解匹配，适用于"给特定注解标记的方法织入切面"的灵活场景
- **连接点 JoinPoint**：在通知中获取方法名、参数、目标对象等信息。
- **综合案例（操作日志）**：实现了一个记录操作日志的切面——通过 `@annotation` 自定义注解标记需要记录的方法，在 `@Around` 中记录操作人、操作方法、参数、执行耗时，插入日志表。这个案例同时用上了切入点表达式、环绕通知、JoinPoint 三大知识点，是本周最有收获的练习之一。

### 2.4 Day14 SpringBoot 原理

- **配置优先级**：命令行参数 > Java 系统属性 > `application-{profile}.yml` > `application.yml` > 默认配置，理解了多环境配置（dev/prod）覆盖机制。
- **Bean 管理**：
    - Bean 获取：通过 `ApplicationContext.getBean()` 手动获取容器中的 Bean
    - 作用域：`singleton`（默认，单例）与 `prototype`（每次获取新建实例），用 `@Scope` 指定
    - 第三方 Bean：对无法加注解的第三方类，通过 `@Bean` 方法注册到容器
- **起步依赖原理**：`spring-boot-starter-*` 本身没有业务代码，本质是"依赖清单"——通过 Maven 依赖传递把一组配套的库拉入工程，并统一管理版本。
- **自动配置原理（重点）**：从 `@SpringBootApplication` → `@EnableAutoConfiguration` → 自动配置类加载（`META-INF/spring/...AutoConfiguration.imports`）→ `@Conditional` 条件装配（按类路径、属性等条件决定是否生效）这一整条链路跟源码梳理了一遍，理解了"为什么引入 starter 后零配置即可运行"。
- **动手实现自定义 starter**：定义自动配置类 + 条件注解 + 配置文件注册，在空项目中引入后自动装配生效。亲手做完后，对自动配置机制的理解从"背概念"变成了"见过实现"。

### 2.5 Day15 Maven 高级

- **分模块设计**：将单体工程按职责拆分为多个 Maven 模块（如 sky-take-out 的父工程 + sky-common / sky-pojo / sky-server），模块间通过依赖建立关系，实现复用与解耦。
- **继承与聚合**：
    - 继承：子模块通过 `<parent>` 继承父工程的依赖管理，配合 `<properties>` + `<dependencyManagement>` 实现**版本统一锁定**，避免各模块依赖版本不一致。
    - 聚合：父工程通过 `<modules>` 声明子模块，一条命令 `mvn install` 即可按依赖顺序构建全部模块。
- **私服**：了解了 Nexus 私服的作用——团队内部依赖的上传下载、无法访问外网的场景下统一从私服拉取依赖。配合本周苍穹外卖的工程结构（典型的分模块聚合项目），这部分理解起来非常直观。

### 2.6 苍穹外卖 Day1：环境搭建与员工登录

- **项目介绍**：B 端管理后台（Web）+ C 端用户端（微信小程序），共 11 张表（employee、category、dish、orders、user 等），前后端分离架构。
- **环境搭建**：
    - 前端工程由 **Nginx** 托管静态页面，并配置**反向代理**：前端请求 `/api/xxx` 经 Nginx 转发到后端 `http://localhost:8080/admin/xxx`，还顺带了解了负载均衡的基本概念。
    - 后端为 **Maven 聚合工程**：父工程 sky-take-out + sky-common（常量、异常、工具类、属性类）+ sky-pojo（DTO/Entity/VO）+ sky-server（Controller/Service/Mapper），与 Day15 学的分模块设计正好互相印证。
    - 数据库：导入 sky_take_out 库及初始数据（含 11 张表），使用 Druid 连接池。
- **员工登录（重点）**：
    - 三层架构：Controller（接收 `EmployeeLoginDTO`，返回 `Result<EmployeeLoginVO>`）→ Service（查询校验）→ Mapper（`@Select` 按用户名查库）。
    - 异常体系：自定义了 `AccountNotFoundException`（账号不存在）、`PasswordErrorException`（密码错误）、`AccountLockedException`（账号被锁定）等业务异常，配合全局异常处理器统一返回错误结果——比 Tlias 中把异常混在一起处理更规范。
    - **MD5 加密**：数据库初始密码为明文 `123456`，登录时用 Spring 的 `DigestUtils.md5DigestAsHex` 加密后比对，避免数据库明文存储密码。
    - **JWT 签发**：登录成功后用 `JwtUtil` 生成携带员工 id 的令牌返回前端；`JwtTokenAdminInterceptor` 拦截器校验每个请求的令牌，通过 `BaseContext`（ThreadLocal）保存当前登录员工信息，供 Service 层取用。
    - **Swagger 接口文档**：集成 Knife4j，通过浏览器页面直接查看和调试接口，配置了文档分组。
- **前后端联调**：通过断点调试追踪了完整请求链路（浏览器 → Nginx → Controller → Service → Mapper → 数据库 → 返回 JSON），第一次直观看到反向代理在整个链路中的位置。

### 2.7 苍穹外卖 Day2：员工管理

- **新增员工**：接收 `EmployeeDTO` → 密码默认设置为 `123456` 的 MD5 值 → 插入数据库；针对 `username` 唯一约束冲突（`SQLIntegrityConstraintViolationException`）做了统一异常处理映射。
- **员工分页查询**：`EmployeePageQueryDTO` 封装查询条件（姓名、状态、页码），结合 **PageHelper** 分页插件 + **动态 SQL**（`<if>` 按条件拼接查询），返回 `PageResult`（总条数 + 数据列表）。与 Tlias 中的分页实现思路一致，但苍穹外卖的查询条件是抽取到 XML 映射文件中管理的，复习了 XML 方式动态 SQL 的写法。
- **启用/禁用员工**：更新 `status` 状态字段，前端以开关形式切换，接口校验不能禁用当前登录账号自己。
- **编辑员工**：先根据 id 查询回显（GET），再提交更新（PUT），更新时填充修改人与修改时间。
- **分类管理**：导入课程提供的分类管理代码（CategoryController / CategoryService / CategoryMapper），通读了新增、分页、修改、启用禁用、删除分类的完整实现，并梳理了分类模块与员工模块在结构上的异同。

## 四、问题与解决方案

| 问题 | 解决方案 |
|------|----------|
| 苍穹外卖启动后登录接口一直返回 401 未授权 | 检查 `WebMvcConfiguration` 中拦截器的 `excludePathPatterns` 配置，将 `/admin/employee/login` 加入放行路径；同时确认前端请求头携带的令牌名称（`admin-token-name`）与后端读取一致 |
| `@Transactional` 事务回滚不生效 | 排查发现异常被方法内 try-catch 捕获吞掉了，且未指定回滚类型。改为不捕获直接抛出（由全局异常处理器处理），或显式指定 `rollbackFor = Exception.class` |
| 事务方法内部自调用不生效（`this.xxx()`） | 自调用不走 Spring 代理，事务切面不会织入。改为注入自身代理调用，或将自调用部分拆到另一个 Service 类中 |
| 多个 AOP 切面通知执行顺序混乱 | 通过 `@Order(数字)` 为切面指定优先级（数字越小越先执行），使日志、事务等切面的执行顺序可控 |
| 自定义 starter 引入后自动配置不生效 | 检查 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件的类全限定名是否写对、自动配置类是否标注 `@Configuration` 且条件注解（`@ConditionalOnClass`）引用的类确实存在 |
| 分模块工程中 sky-server 引用 sky-pojo 的类编译报错 | 父工程下先对依赖模块执行 `mvn install` 安装到本地仓库，再构建依赖方模块；确认各模块 `<parent>` 与依赖声明正确 |
| 新增员工时 `username` 重复导致插入报错 | 捕获 `SQLIntegrityConstraintViolationException`，在全局异常处理器中映射为"用户名已存在"的统一错误提示，而不是把 SQL 异常细节直接返回给前端 |

## 六、总结与思考

本周完成了 JavaWeb 基础阶段的学习收官，并正式迈入企业级项目实战，收获与体会如下：

- **从"学框架"到"看企业项目"的视角切换**：Tlias 是教学级案例，苍穹外卖是贴近真实开发的企业级项目。同样是登录模块，苍穹外卖用自定义异常体系 + ThreadLocal 保存登录用户 + 拦截器统一校验 + 配置属性类（`@ConfigurationProperties`）管理参数，代码组织明显更规范。对照着看两份代码，才真正理解了前几周学的"分层解耦""配置化"在企业项目里是怎么落地的。

- **事务和 AOP 本质上是同一件事**：学 `@Transactional` 时遇到了自调用失效、异常被吞回滚不生效这些坑，后来学完 AOP 才恍然大悟——事务本身就是 AOP 的典型应用（代理 + 环绕通知）。把两个知识点放在一起学，理解深度是单独学任何一个都无法达到的。

- **SpringBoot 从"会用"到"懂原理"**：之前只知道"引入依赖就能跑"，通过跟源码梳理 `@EnableAutoConfiguration` → 自动配置类 → `@Conditional` 条件装配这条链路，再亲手实现一个自定义 starter，终于把"魔法"变成了"机制"。这也是第一次体会到：框架原理不是面试八股，而是排查问题的能力基础。


- **复习是最好的巩固方式**：Day12 的登录认证内容其实上周学过一遍，但当时是"按知识点学"；本周在苍穹外卖项目里"按业务用"了一遍（拦截器排除登录路径、ThreadLocal 传参、JWT 校验），两种视角结合后，这些知识才算真正内化了。

五周下来，从 Java SE 到 JavaWeb 全链路再到企业级项目实战，学习节奏保持稳定。下周继续推进苍穹外卖，并开始接触 Redis 缓存体系。
