## 二、核心学习内容

### 2.1 Day7 缓存商品与购物车

- **缓存菜品（Redis 手动缓存）**：
    - 背景：用户端商品浏览是最高频的读操作，每次都查数据库会给 MySQL 带来较大压力。
    - 实现思路：用户端查询菜品时先从 Redis 读取，缓存未命中再查数据库并写入 Redis；管理端对菜品进行增删改、起售停售等操作时同步清理对应缓存，保证数据一致性。理解了"先更库、再清缓存"的 Cache Aside 模式。
- **缓存套餐（Spring Cache）**：
    - 学习了 `@Cacheable`（查询时缓存，key 可指定 SpEL 表达式如 `#categoryId`）、`@CacheEvict`（数据变更时清除缓存，allEntries 清空整个缓存空间）、`@CachePut`（更新缓存）三个核心注解，并动手完成了入门案例。
    - 与手动 Redis 缓存对比，体会了声明式缓存的优势——只需加注解，无需自己写序列化与存取逻辑；也理解了它的局限——key 规则、缓存与业务代码的隐式耦合需要自己把握。
- **购物车**：
    - 数据库设计：shopping_cart 表，通过 user_id 关联用户，dish_id / setmeal_id 区分菜品与套餐，number 记录数量。
    - 添加购物车：先按"当前用户 + 菜品/套餐"查询是否已存在，存在则数量 +1 并更新，不存在则新增——避免了同一商品产生多条记录。
    - 查看购物车：按当前登录用户（ThreadLocal 中取出）查询列表，菜品与套餐分别展示。
    - 清空购物车：删除该用户全部购物车记录。

### 2.2 Day8 用户下单与订单支付

- **地址簿模块**：导入了地址簿功能代码（增删改查、默认地址设置），了解了"用户地址"这一基础数据从管理到下单使用的完整流程。
- **用户下单（重点）**：
    - 数据库设计：orders（订单主表：订单号、金额、状态、地址快照、下单时间等）+ order_detail（订单明细表：菜品快照、份数、金额），一对多关系。
    - 下单流程：查询购物车 → 校验店铺营业状态、地址是否在配送范围内 → 计算总金额（统一使用 BigDecimal，单价以数据库为准而非前端传值）→ 插入订单主表（初始状态"待付款"）→ 批量插入订单明细 → 清空购物车 → 返回订单号。
    - 订单号生成：时间戳 + 随机数拼装，避免并发下重复。
- **订单支付（微信支付，重点）**：
    - 理解了微信支付的整体流程：后端调用统一下单接口生成预付单 → 返回支付参数 → 小程序端 `wx.requestPayment` 调起收银台 → 用户确认支付 → 微信服务器异步回调通知后端 → 后端校验签名、更新订单状态。
    - 实操要点：微信支付相关配置（商户号、证书、API v3 密钥）全部通过环境变量注入；本地开发使用 Cpolar 内网穿透，让微信服务器能够回调到本地服务；支付结果以**异步回调**为准，不能只依赖前端支付成功的结果。

### 2.3 Day9 项目实战：历史订单与订单管理

课程最后一个项目实战日，根据产品原型与接口文档独立完成两大模块：

- **用户端历史订单**：分页查询历史订单（按状态筛选）、订单详情（含明细）、取消订单（仅"待付款/待接单"状态可取消，已接单的需联系商家）、再来一单（将原订单明细重新加入购物车）。
- **商家端订单管理**：订单多条件搜索（订单号/手机号/状态/日期区间）、各状态订单数量统计、订单详情、接单、拒单（需填拒单原因）、取消订单、派送订单、完成订单——完整走了一遍订单从"待付款 → 待接单 → 已接单 → 派送中 → 已完成"的状态机，以及"已取消/已拒单"等终止状态。
- **已有功能优化**：基于百度地图开放平台（地理编码 + 路线规划接口）实现配送范围校验，用户收货地址与门店距离超过 5 公里则下单失败，体验了第三方 API 从注册、申请 AK 到调用、解析响应的完整对接流程。

### 2.4 Day10 订单状态定时处理、来单提醒和客户催单

- **Spring Task**：学习了 Spring 内置定时任务框架，重点掌握 cron 表达式（秒 分 时 日 月 周，共 6 个域，不支持"年"），使用 `@Scheduled(cron = "...")` 声明定时方法，配合 `@EnableScheduling` 开启。
- **订单状态定时处理**：
    - 超时未支付订单：每隔 1 分钟检查一次，下单超过 15 分钟仍未支付的订单自动置为"已取消"。
    - 超时未完成订单：每天凌晨 1 点检查"派送中"超过 1 小时的订单自动置为"已完成"。
- **WebSocket（双向通信）**：
    - 理解了 WebSocket 与 HTTP 的本质区别——全双工、长连接、服务端可以主动推送，适合来单提醒、在线聊天等实时场景。
    - 服务端通过 `@ServerEndpoint` 声明端点，onOpen / onMessage / onClose / onError 四个回调处理连接生命周期，用 ConcurrentHashMap 维护客户端连接会话。
- **来单提醒**：用户支付成功后，后端向管理端页面推送新订单消息（含订单号、菜品概要、金额），商家端实时弹窗提醒，无需刷新页面。
- **客户催单**：用户点击"催单"按钮，后端将催单消息通过 WebSocket 推送给商家端，形成完整的双向交互闭环。

### 2.5 Day11 数据统计（图形报表）

- **Apache ECharts**：学习了基于 JavaScript 的开源可视化图表库，了解折线图、柱状图、饼图等基础用法，通过 AJAX 从后端接口获取数据后渲染图表。
- **营业额统计**：按日期维度统计营业额（仅统计已支付订单），返回日期列表 + 营业额列表，前端绘制折线图；时间区间查询时注意边界处理（>= 起始日 00:00 且 < 结束日次日 00:00）。
- **用户统计**：统计区间内每日新增用户数与总用户数。
- **订单统计**：每日订单总数、有效订单数（已完成）、订单完成率。
- **销量排名 Top10**：按菜品/套餐销量降序取前 10 名（仅统计已完成订单），通过 SQL 分组聚合 + 排序实现，返回名称与销量，前端绘制柱状图。

### 2.6 Day12 数据统计（Excel 报表）

- **工作台**：管理后台首页的"今日数据"（今日营业额、有效订单、订单完成率、平均客单价、新增用户）与"待办事项"（待接单、待派送数量），代码导入 + 功能测试。
- **Apache POI**：学习了用 Java 操作 Excel 的 POI 库——`XSSFWorkbook` 创建/读取工作簿，单元格样式（字体、边框、合并单元格、对齐）、`DataFormat` 格式化日期，掌握了"写入报表"与"读取文件"两个入门案例。
- **导出运营数据 Excel 报表**：查询近 30 天的运营数据（日期、营业额、订单量、有效订单、订单完成率、平均客单价、新增用户），通过 POI 生成带样式表格的 Excel 文件，设置响应头后以文件流方式下载，浏览器直接打开即可。

## 四、问题与解决方案

| 问题 | 解决方案 |
|------|----------|
| 用户端修改菜品后页面仍显示旧数据（缓存未更新） | 数据变更时同步执行 `@CacheEvict` 清理对应缓存，或手动删除 Redis 中的菜品缓存；明确"先更数据库、再清缓存"的顺序 |
| Spring Cache 缓存命中不到，每次仍查数据库 | 检查 key 生成规则是否一致（如 `#categoryId` 与查询参数对应），以及缓存名称（cacheNames）是否统一 |
| 添加购物车时同一菜品重复添加产生了多条记录 | 添加前先按"当前用户 + dish_id"查询，已存在则数量 +1 并更新，不存在才新增 |
| 下单金额计算出现小数精度问题 | 金额统一使用 BigDecimal，单价从数据库读取而非前端传值，计算时指定精度与舍入方式 |
| 定时任务不执行 | 检查 cron 表达式格式（6 个域，不支持"年"）、方法所在类是否被 Spring 管理、是否添加 `@EnableScheduling` |
| WebSocket 来单提醒收不到消息 | 检查前端连接地址与 `@ServerEndpoint` 路径是否一致、session 是否成功存入容器、推送时机（下单支付成功后）是否正确 |
| 营业额统计结果与预期不符 | 统一统计口径：只统计已支付订单；时间区间用 `>= 起始日 00:00 且 < 结束日次日 00:00`，避免边界日期漏算 |
| 导出 Excel 中文乱码 / 列错位 | 设置响应头 `Content-Disposition` 时对文件名做 URL 编码，单元格按固定列索引写入，日期列用 `DataFormat` 格式化 |

## 六、总结与思考

本周学完苍穹外卖最后六天课程，企业级项目全链路收官。几点核心体会：

- **订单状态机是业务复杂度的集中体现**：订单从"待付款"到"已完成"的每一步流转都对应明确的业务规则和权限边界（谁能取消、谁能接单、拒单要理由），还有超时自动取消/自动完成这类"时间驱动"的状态变更。做完整套订单模块，才真正体会到"业务逻辑"四个字的重量——它比任何框架技术都难，也是最值钱的部分。

- **缓存是"读多写少"场景的银弹，但要付出一致性代价**：给商品浏览加缓存后性能提升明显，但随之而来的是"缓存与数据库如何保持一致"的问题。本周通过"先更库、再清缓存"和 Spring Cache 的声明式清理，把这个问题在项目里落到了实处，也理解了为什么面试总爱问缓存一致性——它是真实业务里躲不开的权衡。

- **微信支付打通后，对"外部集成"有了完整认知**：统一下单、异步回调、验签、内网穿透调试……微信支付是本周最复杂的模块，但走通之后发现所有第三方支付、登录的本质都一样：遵循对方文档、正确处理回调、以服务端结果为准。这种对接能力在真实工作中会反复用到。

- **项目实战是最快的能力检验**：Day9 独立完成订单管理时，第一次真切感受到"需求分析 → 接口设计 → 开发 → 测试"已经变成肌肉记忆；加入百度地图配送校验这类"已有功能优化"，也更接近真实开发中"改别人代码"的场景。

- **系统从"被动响应"升级到"主动服务"**：Spring Task 让系统能自己处理超时订单，WebSocket 让服务端能主动推送消息。这一周之后，苍穹外卖已经是一个"完整闭环"的系统：有人下单、能支付、能提醒、能统计、能导出报表。

七周下来，从 Java SE 到 JavaWeb 全链路，再到完整落地一个企业级单体项目，学习目标基本达成。下周进入八股文复习试点阶段，把项目里用到的知识系统化、原理化，为后续面试和进一步学习打基础。
