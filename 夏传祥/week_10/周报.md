## 二、核心学习内容

### 2.1 存储引擎与 MySQL 体系结构

先把 MySQL 的整体结构理了一遍，一条 SQL 从客户端发出到返回结果，中间要经过连接器、分析器、优化器、执行器这几层，最后才落到存储引擎上，这个链路搞清楚之后，后面学索引和 explain 就有了位置感。

存储引擎重点对比了 InnoDB、MyISAM 和 Memory 三个。InnoDB 支持事务和外键，用行级锁，崩溃后可以靠 redo log 恢复，是 5.5 之后的默认引擎；MyISAM 只有表锁，不支持事务，胜在查询速度快、占用空间小，会把行数单独存起来，所以 count(*) 不查具体数据就能返回；Memory 把数据放内存里，速度最快但断电即失，一般只拿来做临时表。就苍穹外卖而言，所有表用的都是 InnoDB，因为下单这类操作必须依赖事务保证一致性，这个选择没有悬念。

### 2.2 索引（本周分量最重的一块）

**结构层面**，把 B 树、B+ 树、哈希三种结构都推了一遍。B+ 树相比 B 树做了两个关键改动，一是只有叶子节点存数据，非叶子节点只放索引，这样单个节点能容纳的键更多，树就更矮更胖，磁盘 IO 次数更少；二是叶子节点之间用双向链表串起来，范围查询和排序就不用回到树顶重新找了。哈希结构查等值确实快，但范围查询完全没法做，所以 InnoDB 只在自适应哈希索引里内部使用，不开放给开发者手动建。这里还做了一道思考题，红黑树和二叉树为什么不适合做索引，答案还是落在树高上，数据量一大树就太深，IO 次数撑不住。

**分类和语法**这部分过得比较快，主键索引、唯一索引、常规索引、联合索引的区别，加上 create index、show index、drop index 几条语句，之前课程里都碰过。

**性能分析**学了四件工具，show global status 看执行频次，慢查询日志抓超过 long_query_time 的语句，show profiles 看一条 SQL 各阶段的耗时，以及最重要的 explain 执行计划。explain 的输出字段里，type 的等级从好到差是 system、const、eq_ref、ref、range、index、ALL，出现 ALL 就说明全表扫描了；key 能看到实际用到的索引，rows 是预估扫描行数，Extra 里的 Using index 代表覆盖索引、Using filesort 代表文件排序需要警惕。

**使用规则**是这一块的核心。最左前缀法则的道理在于联合索引的排序方式，先按第一列排，第一列相同再按第二列排，所以查询条件跳过第一列直接用第二列，索引就失效了。索引失效的常见情况整理了几种，在索引列上做函数运算或者算术操作、字符串不加单引号引发隐式类型转换、like 以百分号开头、or 连接的条件里有一边没索引，这几种情况都会让优化器放弃索引走全表扫描。覆盖索引和回表的概念也理顺了，普通索引查到主键还要回聚簇索引再取一次数据，这就是回表，如果查询的列全部包含在索引里，就不用回表了，这也是尽量别用 select * 的底层原因。前缀索引拿长字符串来说，可以只索引前面一部分字符来省空间，代价是覆盖索引用不了了。单列索引和联合索引的选择上，业务里多个条件一起出现的场景，建联合索引比建一堆单列索引更合适。

**设计原则**归纳下来就是几条，表数据量超过百万才考虑建索引，字段有唯一性约束要建唯一索引，频繁作为查询条件、排序、分组字段的列适合建索引，字符串长的用前缀索引，还有一个容易忽略的点，要尽量避免更新频繁的字段上建索引，因为维护索引本身有成本。

### 2.3 SQL 优化

插入数据方面，批量插入用一条 insert 带多组 values，比循环单条插入省掉了大量的网络交互和事务提交；数据量特别大的时候可以手动提交事务，或者用 load 指令导入。主键优化的要点是主键要尽量短、插入尽量顺序，UUID 做主键的问题就在这里，它是无序的，每次插入都可能插到页的中间位置，引发页分裂，而自增主键永远往最后一页追加，顺序写效率高得多。

order by 优化区分了两种排序方式，Using index sort 是直接利用索引的有序性，Using filesort 是把数据捞到排序缓冲区里再排，后者明显更慢，优化方向就是让 where 和 order by 的字段尽量共同命中一个索引。group by 同样遵循最左前缀，分组字段能用上索引就能省掉排序。

limit 优化针对的是深分页问题，拿 limit 1000000, 10 来说，MySQL 要先扫描并丢弃前一百万行，白白做了大量无用功，解决办法是先用覆盖索引查出目标区间的主键，再用主键关联回表取数据，扫描量会小很多。count 优化把几种写法的效率排了序，count(主键) 和 count(1) 都比 count(普通字段) 快，因为普通字段要判断是否为 null，而官方推荐直接写 count(*)，InnoDB 对它做了专门优化，会挑最小的可用索引来遍历。

update 优化只有一条但很关键，where 条件必须走索引，否则行锁会升级成表锁，并发写入直接被串行化，这一条和后面锁的章节是连着的。

### 2.4 视图、存储过程与触发器

视图是把一条查询封装成虚拟表，本身不存数据，用的时候实时查底层表，with cascaded check option 和 with local check option 控制着通过视图做的更新能不能超出视图的定义范围。

存储过程把变量、if 判断、case、while、repeat、loop 循环、游标和条件处理程序都过了一遍，存储函数和它的区别主要在必须有返回值。触发器则是绑定在表上的自动执行逻辑，insert、update、delete 各配 before 和 after 两种时机，通过 new 和 old 引用变化的行。

这三样东西学下来，定位也清楚了，就互联网 Java 项目而言，存储过程和触发器基本属于禁用品，阿里巴巴开发手册里明确不允许，理由是逻辑藏进数据库之后难调试、难扩展，业务分层也会被破坏。苍穹外卖里公共字段自动填充这个需求，传统做法正是用触发器实现，项目里用的是 AOP 切面加自定义注解在应用层做，逻辑可见、可调试，也符合分层原则，这个对比在面试里是能讲出深度的点。

### 2.5 锁

锁按照粒度分成三级。全局锁用 flush tables with read lock 把整库置为只读，全库逻辑备份的时候用，代价是备份期间整个库不能写，InnoDB 其实可以靠事务的原子性做到一致性备份，一般不需要它。

表级锁里有三种，表锁本身锁住整张表，lock tables ... read/write 加锁；元数据锁 MDL 是系统自动加的，增删改查加读锁，DDL 加写锁，它的作用是防止一个事务还在用表的时候表结构被别人改了，这里有个经典的坑，事务里查了表没提交，另一个会话对这张表做 DDL 就会被 MDL 卡住，进而把后面的普通查询也全堵住；意向锁是为了让表锁和行锁能共存而设计的，事务给某行加锁之前，会先给表加一个意向锁做标记，这样表锁操作只需要检查意向锁就知道表里有没有行级锁，不用逐行去扫。

行级锁是 InnoDB 特有的，也是重点。行锁锁的是索引上的记录而不是物理行，所以 update 的 where 条件不走索引时，所有记录都会被锁住，效果上等同于表锁，这一点和 SQL 优化章节里 update 那条规则完全对上了。行锁分共享锁和排他锁，共享锁之间兼容，排他锁和谁都不兼容，普通 select 默认不加锁，select ... lock in share mode 加共享锁，select ... for update 和增删改加排他锁。间隙锁锁的是索引记录之间的开区间，临键锁是行锁加间隙锁的组合，锁的是左开右闭区间，RR 隔离级别下默认加的就是临键锁，它存在的意义是阻止别的事务往区间里插新行，幻读就是这么被解决的。这一部分动手做了两个会话的对照实验，一个会话开事务加锁，另一个会话去做更新和插入，把行锁、间隙锁、临键锁的阻塞行为都实际观察了一遍。

### 2.6 InnoDB 架构与事务原理

逻辑存储结构从大到小是表空间、段、区、页、行，页是 InnoDB 管理数据的最小单位，默认 16KB。内存结构里最重要的是 Buffer Pool，数据页的读写都先经过它，命中了就不用碰磁盘，配套的还有 Change Buffer，写非唯一二级索引的时候如果页不在内存里，先把变更记录下来，等页加载了再合并，省掉一次随机读；自适应哈希索引是引擎自己根据访问模式建的，不用人工干预；日志缓冲是 redo log 写盘前的暂存区。磁盘结构上主要记了系统表空间、独立表空间，以及 doublewrite buffer 这种防止页断裂的机制。

事务原理这一块把两大日志的作用彻底理清了。redo log 是物理日志，记录的是某个页做了什么修改，它的价值在崩溃恢复，事务提交时先把 redo log 落盘，数据页哪怕还没刷回去，重启后也能按日志重放恢复，这种先写日志再写磁盘的策略就是 WAL，用顺序写换掉了随机写，性能和安全都顾到了。undo log 是逻辑日志，记录的是反向操作，insert 对应 delete，update 对应反向 update，它一方面支撑回滚，另一方面给 MVCC 提供历史版本，每条 undo 记录用 roll_pointer 串成版本链，这条链就是多版本并发控制的数据基础。

### 2.7 MVCC

MVCC 全称多版本并发控制，目的是让读写互不阻塞，普通 select 属于快照读，不加锁，靠 undo log 版本链读历史数据；select ... for update 和增删改属于当前读，必须读最新版本，靠加锁保证。

实现依赖三样东西。一是隐藏字段，每行记录都带着 DB_TRX_ID，也就是最近修改这行的事务 id，还有 DB_ROLL_PTR 指向 undo log 里的上一个版本；二是版本链，多次修改把各个版本串起来，最新的数据在链头；三是 ReadView，它里面有创建时刻还活跃的事务 id 列表，判断某个版本可不可见，就是拿版本的 DB_TRX_ID 和这个列表比，已提交的、创建 ReadView 之前就结束的，可见，还没提交的、创建之后才开启的，不可见，不可见就顺着版本链往下找。

RC 和 RR 两个隔离级别的差别，最后就落在 ReadView 的生成时机上，RC 每次快照读都生成一个新的 ReadView，所以能看到别的事务新提交的数据，不可重复读就是这么来的；RR 只在事务里第一次快照读时生成一次，之后一直复用，整个事务看到的都是同一个版本，可重复读的问题就不存在了。之前背隔离级别特性的时候一直觉得抽象，这次从 ReadView 的机制推下来，两个级别的行为差别完全能自己推出来，算是把这块硬骨头啃下来了。

## 三、本周实践进展

1. **explain 实战**：在苍穹外卖的库上对订单表和菜品表的常用查询逐个跑了 explain，把 type、key、rows、Extra 几个字段对着执行计划逐一核对，确认了按 user_id 查订单这类高频查询有索引可用，也找出了两处走全表扫描的语句，补建了索引后复查执行计划，type 从 ALL 提到了 ref。

2. **索引失效验证**：把课上讲的失效场景在本地库逐个复现了一遍，对 create_time 用函数、字符串条件不加引号、like 以百分号开头、联合索引跳过最左列，四种写法都用 explain 确认了 key 为 NULL，把"背过的规则"变成了"亲眼见过的现象"。

3. **锁行为双会话实验**：开两个客户端会话，一边开事务对某行加排他锁不提交，另一边分别做更新、插入到相邻区间、普通查询三种操作，观察到了行锁阻塞更新、间隙锁阻塞插入、快照读不阻塞的完整现象，RR 级别下临键锁的范围也用 explain 之外的阻塞行为反推验证了。

4. **深分页与 count 优化对比**：造了一批测试数据，对 limit 大偏移量的查询做了优化前后的耗时对比，覆盖索引加子查询的写法把扫描行数降了两个数量级；同时用 show profiles 对比了 count(*)、count(主键)、count(字段) 三种写法的实际耗时，和课上的结论对上了。

5. **MVCC 推演练习**：拿两个会话交错的时序图，手动推了 RC 和 RR 两种级别下每次 select 的 ReadView 内容和可见性判断，各推了三组场景，推完之后再回头看隔离级别的定义，已经能自己解释每个特性是怎么来的了。

## 四、问题与解决方案

| 问题 | 解决方案 |
|------|----------|
| 联合索引明明建了，查询却没用上 | 用 explain 查看后发现条件跳过了最左列，回到最左前缀法则，联合索引按列的顺序逐级排序，跳列就失效，调整查询条件或者重建索引的列顺序解决 |
| 想不明白 B+ 树为什么比 B 树适合做索引 | 从磁盘 IO 的角度推了一遍，非叶子节点不存数据，单页能放更多键，树高更低，同样数据量下 IO 次数更少，叶子链表又解决了范围查询，两点合起来才是完整答案 |
| update 语句把别的会话全堵住了 | 排查发现 where 条件里的字段没建索引，行锁退化成了锁全表记录，给条件字段补上索引后恢复成正常的行级锁，这也反过来验证了行锁锁的是索引记录这个结论 |
| DDL 语句执行卡住，后面的查询也跟着排队 | 定位到是 MDL 元数据锁，有个事务查过这张表没提交，持有读锁，DDL 要拿写锁只能等，它后面的所有请求又排在 DDL 后面，杀掉长事务或者等它提交后恢复，生产上的教训是事务别太长、DDL 前先查有没有未提交事务 |
| RC 和 RR 的区别背了又忘 | 不再背定义了，改从 ReadView 的生成时机去推，RC 每次快照读都新建，RR 只用第一次的，两个级别的所有行为差异都能从这一个差别推出来，理解了机制之后就不用背了 |
| count(*)、count(1)、count(字段) 分不清用哪个 | 跑了对比实验加上看文档，count(字段) 要判断 null 最慢，count(主键) 和 count(1) 差不多，官方推荐 count(*)，InnoDB 会自动选最小的索引树来遍历，以后统一写 count(*) |
| 深分页查询越翻越慢 | 用 explain 确认了 limit 1000000, 10 要先扫一百万行再丢弃，改成先用覆盖索引查出目标段的主键，再 join 回表取整行，扫描量大幅下降，这个写法已经记进了 SQL 优化的笔记 |

## 五、总结与思考

这一周把 MySQL 进阶完整走了一遍，回头看，收获可以归成三点。

一是索引这一块的价值最大，从 B+ 树的结构推到最左前缀，再推到各种失效场景，最后用 explain 验证，整条线是自洽的，以前零散背过的规则现在都能从树的排序方式推出来，面试被连着追问三层也不怕了，因为每一层的答案都是上一层的自然延伸。

二是 MVCC 是这周最难啃也最值得啃的部分，隐藏字段、版本链、ReadView 三样东西单独看都不复杂，难的是把它们串起来解释隔离级别，啃下来之后有个很直接的体会，背特性和懂机制完全是两种掌握程度，前者忘得快，后者能自己推。

三是这周也修正了一个之前的判断，原先觉得存储过程和触发器可以完全跳过，跟着视频过了一遍之后发现，了解它们的机制反而让"为什么互联网项目不用"这个结论更有说服力，拿公共字段自动填充来说，能讲清楚触发器怎么做、为什么项目里改用 AOP 做，比单纯说"规范不允许"要扎实得多，知道一样东西为什么被淘汰，和从来不知道它，在面试里是两种完全不同的表现。

到这里，上周评估里划定的 MySQL 面试级范围已经基本覆盖完，索引、事务、锁、MVCC、日志这些高频考点都有了机制层面的理解，接下来要做的是把这些内容和苍穹外卖的业务场景再对一遍，把每个知识点都准备一个项目里的实例，让八股和项目真正咬合起来。
