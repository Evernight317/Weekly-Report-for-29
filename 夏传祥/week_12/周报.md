## 二、核心学习内容

### 2.1 LangChain 理论概述

先把框架的背景和定位理清楚了。LangChain 是 2022 年 10 月底由哈佛大学的 Harrison Chase 发起的开源 AI 工程开发框架，发布时间比 ChatGPT 问世还早一个月，Lang 指大语言模型，Chain 指把大模型与其他组件连接成链来构建 AI 应用。课程里用 AB 法则给它下了一句话定义：就是一套把大模型和外部世界连接起来的工具代码。

六大核心模块是这周反复出现的骨架——Models（模型）、Memory（记忆）、Retrieval（检索）、Chains（链）、Agents（智能体）、Callback（回调），六个组件之间耦合非常松散，没有固定调用顺序和接口，开发者可以自由组合。1.0 版本的架构走的是轻核心加模块化的路子：langchain-core 提供基础抽象和 LCEL 表达式语言，langchain-community 承载第三方集成，LangGraph 负责协调多个 Chain、Agent、Tools 完成复杂任务并支持循环调用。生态整体分三层，底层是架构（LangChain 和 LangGraph），中间是组件（Integrations 集成模块），顶层是部署（LangGraph Cloud 和 LangSmith）。

课程对 LangChain 的评价很客观，它像 AI 界的 Spring 框架，生态强、资源多、上手最快，但文档更新跟不上版本迭代、为了兼容所有模型封装层层过深、版本之间不兼容的问题也不少，所以学法上定的策略是"搞懂核心逻辑，用到什么查什么，把它当工具箱而不是教科书"。还有一个对 Java 背景的我很友好的点：课程把大模型应用技术架构直接对标到了熟悉的三层架构，controller、service、dao/mapper 各司其职的位置关系在 LLM 应用里同样成立，Java 生态里也有对标的 LangChain4j 和 Spring AI。

### 2.2 模型接入与 HelloWorld

动手前先把大模型服务平台摸了一遍，阿里云百炼、DeepSeek、OpenRouter、百度千帆、硅基流动这些平台的注册、充值、创建 API-Key 流程都过了一次，本周实操主要用阿里百炼的通义千问，辅以 DeepSeek。调用大模型的"三件套"记熟了：API Key、模型名、调用地址（base_url），所有调用都基于 OpenAI 协议标准或官方推荐规则，这也是多模型能方便切换的前提。

HelloWorld 写了三个版本。V1 零基础版用 LangChain 1.0 的 `init_chat_model` 统一入口接入 qwen-plus，对比了 0.3 版本 `ChatOpenAI` 的旧写法，明确了 1.0 是当前主流；V2 进阶版实现了多模型共存，通义和 DeepSeek 同时实例化按需调用，其中 DeepSeek 的模型名有讲究，deepseek-chat 对应非思考模式，deepseek-reasoner 对应思考模式；企业级版本加上了异常处理、日志配置和流式输出，密钥全部走 dotenv 从 .env 文件读取，杜绝硬编码。

### 2.3 Model I/O 大模型接口

Model I/O 是 LangChain 与大模型交互的核心组件，作用是标准化各家模型的输入输出，一句话概括就是三件套：输入提示（Format，Prompt Template 把原始数据格式化成模型能处理的形式）、调用模型（Predict，通用接口调不同的 LLM）、输出解析（Parse，从模型推理结果里提取信息并规范化，格式化成 JSON 这类结构化数据）。

这一章最有价值的是把 `openai.OpenAI` 和 `langchain_openai.ChatOpenAI` 的区别彻底理清了：前者是 OpenAI 官方原生 SDK，底层、纯粹、贴近原生 API 参数；后者是 LangChain 生态的高层适配器，把模型能力适配进来，好与提示词模板、链、代理、记忆这些组件无缝协作。选型结论是简单调用用原生 SDK，轻快纯净；复杂工作流用 ChatOpenAI，强全易扩展。同时还掌握了 init_chat_model 的标准化参数（temperature 等），注意到这些参数只对官方集成包的模型生效，community 包里的第三方模型不受此约束；模型返回的是 AIMessage 消息对象，type、content、response_metadata 这些属性的含义都过了一遍。

### 2.4 Ollama 本地大模型部署

Ollama 是本地大模型运行工具，装好之后模型就在自己机器上跑，数据不出本机。实操走完了全流程：安装 Ollama、通过 OLLAMA_MODELS 环境变量把模型存储目录自定义到 D 盘（默认位置在 C 盘，模型动辄几个 GB 很快撑爆系统盘）、用 `ollama pull` 拉取模型、`ollama run qwen:4b` 和 `deepseek-r1:14b` 本地跑通对话，常用命令 list、rm、cp、show 也都练了一遍。最后在 LangChain 里通过 langchain-ollama 包把本地模型接了进来，云端 API 和本地模型两种接入方式都掌握了。

### 2.5 Prompt 提示词模板与模型调用方法

Prompt 的演化历程理出了一条清晰的线：最初就是纯字符串提问，然后引入占位符动态插入内容（Prompt Template），再发展到多角色消息——把消息按角色分开，设置功能边界，增强上下文感知。四大角色消息类型是这块的骨架：SystemMessage 设定 AI 的行为边界和角色定位，HumanMessage 是用户输入，AIMessage 是模型输出（可以是文本也可以是调用工具的请求），ToolMessage 承载函数调用的结果（1.0 版本叫 ToolMessage，0.3 叫 FunctionMessage）。

模型调用方法一共六个，按"同步/异步 × 单条/流式/批量"排成一个矩阵：invoke 普通调用等全部推理完成再返回，ainvoke 异步版本适合大批量请求或 Web 服务场景不阻塞主线程，stream 流式响应生成一点返回一点，astream 是异步流式，batch 批量提交并行处理提升吞吐，abatch 是异步批量。

提示词模板部分投入的时间最多。PromptTemplate 是文本生成模型的基础模板，创建方式有构造方法和 from_template 两种，核心参数 template、input_variables、partial_variables 各自的作用弄清楚了，partial_variables 能预先固定部分变量、留其他变量动态填充；格式化方法有三个，format 返回字符串，invoke 返回 PromptValue 对象，partial 返回可以继续格式化的新模板。ChatPromptTemplate 面向多角色多轮对话场景，用 from_messages 创建，列表元素支持元组、字典、消息对象、消息模板等多种类型。MessagesPlaceholder 解决"不确定消息何时生成、要插入几条"的场景，显式和隐式两种用法都练了，这是后面接聊天历史记忆的基础。还了解了 FewShotPromptTemplate（少样本示例教学）和 PipelinePromptTemplate（多个提示词组合），以及把 prompt 存成 JSON/YAML 文件外部加载的做法，方便提示词的管理维护。

### 2.6 Parser 输出解析器

模型返回的天然是字符串，但实际应用要的是能继续走逻辑处理的结构化数据，输出解析器就是架在模型和最终输出之间的转换层，作用有四个：指定格式输出、数据校验、解析失败时的错误处理、生成格式要求提示词。两大核心方法是 parse（把输出格式化成指定格式）和 get_format_instructions（生成一段格式说明字符串塞进提示词，指导模型按格式输出）。

常用的两个解析器都写了代码：StrOutputParser 最简单，从结果里提取 content 字段转字符串；JsonOutputParser 把自由文本转成结构化 JSON，实现方式有两条路，一是用户自己在提示词里指明返回 JSON 格式，二是借助 get_format_instructions 生成格式说明交给模型。进阶部分学了结构化输出的两种 Python 原生方案，TypedDict（3.8+ 标准库）和 Pydantic 配合 Annotated（3.9+），能让模型输出直接映射成带类型约束的数据结构，这块对写惯了 Java 强类型代码的我来说格外亲切。

## 四、问题与解决方案

| 问题 | 解决方案 |
|------|----------|
| init_chat_model 接入通义时报 "Unable to infer model provider for model='qwen-plus'" | 通义走的是 OpenAI 兼容模式，框架无法从模型名自动推断提供商，显式传入 `model_provider="openai"` 并配上百炼的 base_url 解决 |
| Windows 下 load_dotenv 读取 .env 文件中文注释乱码 | 指定编码 `load_dotenv(encoding='utf-8')`，避免默认编码与文件编码不一致 |
| API Key 直接写在代码里有泄露风险 | 全部抽到 .env 文件，用 dotenv 加载后通过 os.getenv 读取，代码仓库不提交 .env |
| Ollama 默认把模型存到 C 盘，几个模型下来系统盘吃紧 | 新建 OLLAMA_MODELS 环境变量指向 D 盘目录，把已有模型文件迁移过去后重启服务生效 |
| pip 安装依赖速度极慢 | 切换清华镜像源，并用 `pip config set global.index-url` 设为虚拟环境默认 |
| 跟着旧教程写的代码在新版本报错，0.3 和 1.0 的 API 对不上 | 认识到 LangChain 版本迭代快、文档滞后是常态，以 1.0 的 init_chat_model 写法为主线，0.3 的 ChatOpenAI 写法只做对照了解，遇到 API 对不上先查版本变更记录 |
| 让模型返回 JSON 时格式时好时坏，解析经常失败 | 双管齐下，提示词里明确格式要求并给示例，同时用 JsonOutputParser 的 get_format_instructions 生成标准格式说明拼进提示词，解析失败率明显下降；要求严格的场景改用 Pydantic 结构化输出兜底 |

## 五、总结与思考

这一周从平台切换到代码，几个体会比较深：

- **有 Spring 的底子，LangChain 学起来处处似曾相识**。init_chat_model 的统一入口像工厂方法加自动配置，六大模块松耦合自由组合像 IOC 容器里的组件装配，输出解析器把模型的自由文本约束成结构化数据，像极了接口层用 DTO 收参数、VO 出数据的思路，课程自己也把大模型应用架构对标到了 controller/service/dao 三层。框架不同，工程思想是通的，这也是我坚持先学扎实 Java 再碰 AI 框架的原因，底层认知可以直接迁移。
- **上周的平台和这周的代码终于接上了**。在 Coze 和 Dify 上拖"大模型节点""提示词节点"的时候只知道填参数，这周写完 init_chat_model、ChatPromptTemplate、JsonOutputParser 之后回头再看，平台上每个节点对应的就是这些代码组件，低代码是封装，LangChain 是封装下面的那一层。两条路线不是二选一，是同一件事的两个楼层。
- **Prompt 从凭感觉变成了工程**。以前写提示词全靠试，这周把"字符串 → 占位符模板 → 多角色消息"的演化走了一遍，尤其是 SystemMessage 定边界、MessagesPlaceholder 留记忆接口、get_format_instructions 约束输出格式这些手段，让提示词变成了可管理、可复用、可版本化的工程资产，这是"会玩 AI"和"能开发 AI 应用"的分水岭。
- **Ollama 打开了本地部署的认知**。模型跑在自己机器上，数据不出本机，qwen:4b 这种小模型的响应速度完全可用，对隐私敏感场景和断网环境的价值很直观，也让我对企业级私有化部署那条路线有了初步概念。
