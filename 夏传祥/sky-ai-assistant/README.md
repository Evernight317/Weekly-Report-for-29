# 苍穹外卖 AI 助手

给《苍穹外卖》加一个 AI 点餐与客服助手。它是一个**独立的 Python 服务**，通过 HTTP 调用苍穹外卖后端的 `/user/**` 接口，
**业务代码零侵入**（后端仅修复了一处数据缺陷，见「已知问题」）。

支持自然语言点餐、订单查询与操作、平台规则问答，多 Agent 路由，带跨会话记忆。

## 功能

| 模块 | 能力 |
|---|---|
| 点餐 | 浏览分类、按分类看菜（含口味）、加购物车、查看购物车 |
| 订单 | 历史订单分页查询（可按状态过滤）、下单、取消、催单、再来一单 |
| 客服 | 基于《平台规则》的 RAG 问答，回答标注条款编号 |
| 编排 | 主管 Agent 按意图路由；复合问题串行调用多个子助手后汇总 |
| 记忆 | 基于 SqliteSaver 的跨进程会话记忆，按 `thread_id` 隔离 |

## 架构

```
┌───────────────────────────────────────────┐
│ Gradio 界面 (run_web.py) / CLI (run.py)   │
└───────────────────┬───────────────────────┘
                    │
        ┌───────────▼────────────┐
        │ Supervisor（主管）      │  路由 + 写操作确认 + 会话记忆
        └──┬──────────────────┬──┘
           │                  │
   ┌───────▼────────┐  ┌──────▼───────────┐
   │ 订单 Agent     │  │ 客服 Agent        │
   │ 10 个工具      │  │ RAG 检索 44 条规则 │
   └───────┬────────┘  └──────┬───────────┘
           │                  │
   ┌───────▼────────┐  ┌──────▼───────────┐
   │ 苍穹外卖后端    │  │ 本地 bge-m3       │
   │ :8080 /user/** │  │ Ollama :11434    │
   └───────┬────────┘  └──────────────────┘
           │
     MySQL / Redis
```

**为什么分层**：单 Agent 挂 11 个工具时工具选择准确率明显下降；而"操作订单"和"回答规则"是两类完全不同的能力，
拆开后每层的提示词与工具集都能保持聚焦。

## 快速开始

### 1. 前置服务

```
MySQL → Redis（必须带 redis.windows.conf 启动）→ SkyApplication:8080 → Nginx
Ollama:11434（先执行 ollama pull bge-m3）
```

### 2. 安装与配置

```bash
pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/
cp .env.example .env          # 填入模型 Key；LangSmith Key 可选
```

### 3. 生成凭证与知识库索引

```bash
python scripts/gen_token.py       # 签发测试用户 JWT → data/token.txt
python scripts/build_index.py     # 切分 → 向量化 → data/index.json（44 条 × 1024 维）
```

### 4. 启动

```bash
python run_web.py          # Gradio 界面，http://127.0.0.1:7860
python run.py              # 订单 Agent CLI
python run_kb.py           # 客服 Agent CLI
python run_supervisor.py   # 主管 Agent CLI（整合两个子 Agent）
```

## 设计要点

| 决策 | 理由 |
|---|---|
| **工具参数只留语义** | `amount` 由工具从购物车实时计算，绝不让模型传；金额算错即资损。`page`/`pageSize` 同样不暴露给模型 |
| **状态参数用中文词而非数字** | 模型对"待接单"的语义把握优于魔法值 `2`；映射表集中在模块级，一张表派生正反两个方向 |
| **写操作确认上移到主管层** | 子 Agent 没有可对话的用户，`human-in-the-loop` 在工具化后会断。主管先复述待确认内容，用户明确确认后才下放；子 Agent 侧再加"无明确确认不执行写操作"的兜底 |
| **按条款切分而非定长切分** | 语料本身是结构化的 44 条条款。定长切分会把多条规则混成一块，出处只能到"第三章"，且多主题平均会稀释向量、降低相似度 |
| **阈值 0.55 / K 上限 4 由数据确定** | 6 组查询实测：相关 top1 ∈ [0.655, 0.804]，无关 0.493，取中间并留两侧余量；K=4 是为了让"发票怎么开"带上排第 4 的 6.1 |
| **记忆只放在主管层** | 子 Agent 编译为无状态图，每次调用是独立任务；避免 `thread_id` 冲突与子 Agent 间状态污染 |
| **工具输出即提示词** | 无结果时返回明确文案而非空串；错误信息写成可读提示，让模型能自行纠错重试 |

## 技术选型与放弃的方案

| 选择 | 说明 |
|---|---|
| 本地 Ollama + bge-m3 | 模型服务商无 embedding 接口；bge-m3 中文检索效果好，离线、免费、无额外依赖 |
| numpy 暴力检索 | 44 条规模下比任何向量库都快，且分数可直接打印，便于用数据确定阈值 |
| LangGraph ReAct + 子图工具化 | 复用同一份 `build_graph(tools, prompt)`，三个入口共用图代码 |

**主动放弃的**：

- **Redis Stack 向量库**：官方无 Windows 版，需 Docker/WSL。为 44 条规则引入容器化成本不划算；
- **Chroma / FAISS**：当前规模无收益。`app/rag.py` 已封装 `retrieve()`，将来替换只改一个函数；
- **微信支付**：后端为桩实现（`paySuccess` 直接改单），未接真实支付，本文档不宣称支持支付。

## 已知问题

1. **后端订单明细份数丢失（已修复）**：`OrderDetailMapper.insertBatch` 漏插 `number` 列，被建表默认值 `1` 掩盖，
   导致明细份数与订单金额不一致、销量统计失真。已补列并同步 `target/classes`；**存量数据未回填**，
   修复前创建的订单明细份数仍为 1。
2. **发票 / 会员 / 优惠券**仅存在于规则语料，系统未实现。客服提示词已要求区分"规则允许"与"系统支持"。
3. **界面非流式**，复合请求端到端 8–12 秒。
4. **后端 `cancel` / `repetition` 未校验订单归属**：任意登录用户知道订单 id 即可操作他人订单（后端缺陷，未修改）。

## 目录结构

```
sky-ai-assistant/
├── app/                 # 运行时
│   ├── client.py        # HTTP 封装：异常分层 + 业务码收敛
│   ├── tools_order.py   # 10 个订单工具
│   ├── tools_kb.py      # 检索工具
│   ├── rag.py           # 检索实现（唯一）
│   ├── graph.py         # ReAct 图，参数化 tools / prompt
│   ├── supervisor.py    # 子 Agent 工具化 + 主管图
│   └── prompts.py       # 三套提示词集中管理
├── knowledge/           # 语料（进 git）
├── data/                # token 与索引（生成物，gitignore）
├── scripts/             # 建索引、签 token、连通性测试（车间）
└── run*.py              # 四个入口
```
