## 二、核心学习内容

### 2.1 Day3 菜品管理

- **公共字段自动填充（重点）**：
    - 背景：新增/修改操作都要为 `create_time`、`create_user`、`update_time`、`update_user` 四个公共字段赋值，每个 Mapper 方法里都重复写一遍既冗余又容易遗漏。
    - 方案：自定义 `@AutoFill` 注解 + AOP 切面统一处理。自定义枚举 `OperationType`（INSERT / UPDATE）标注操作类型，切面通过 `execution(* com.sky.mapper.*.*(..)) && @annotation(autoFill)` 精准匹配标注了注解的 Mapper 方法，在 `@Around` 通知中通过**反射**为实体的公共字段赋值，当前登录用户 id 从 `BaseContext`（ThreadLocal）中获取。
    - 这正好把上周学的 AOP（自定义注解、切入点、环绕通知、JoinPoint）串起来用在了真实项目里，学完知识点后亲眼见到它的落地，理解深度完全不一样。

- **新增菜品**：接收 `DishDTO`（含名称、分类、价格、口味列表 `List<DishFlavor>`），先插入菜品表，再循环插入口味表（dish_flavor），两步操作由 `@Transactional` 保证事务一致性。

- **菜品分页查询**：`DishPageQueryDTO` 封装查询条件（名称、分类、状态、页码），PageHelper 分页 + 动态 SQL `<if>` 条件拼接，返回 `PageResult`。菜品表只存分类 id，查询结果通过多表联查关联分类名称，用 `DishVO` 封装后返回前端展示。

- **删除菜品（批量）**：接收 ids 列表，`<foreach>` 生成 `IN (?,?,?)` 批量删除。两个关键业务规则：**起售中的菜品不能删除**；**被套餐关联的菜品不能删除**（删除前先查 setmeal_dish 关联表），违规时抛出自定义 `DeletionNotAllowedException`，由全局异常处理器统一返回提示信息。

- **修改菜品**：先根据 id 查询菜品及口味列表回显（返回 `DishVO`），提交更新时先删除该菜品的全部口味再重新插入，保证口味数据与页面一致。

- **菜品起售停售（作业）**：根据产品原型完成需求分析，分析出"起售中的菜品不能被删除、新增菜品默认停售"等业务规则，设计接口 `PUT /admin/dish/status/{status}`，完成代码实现，并分别通过 Swagger 接口文档和前后端联调两种方式进行功能测试。

### 2.2 Day4 项目实战：套餐管理

Day4 是课程安排的"项目实战日"，要求在无讲解的情况下独立完成套餐管理模块：

- **需求分析与接口设计**：根据产品原型分析业务规则，梳理出分类表、菜品表、套餐表、口味表、套餐菜品关系表（setmeal_dish 中间表）之间的关系，独立完成 RESTful 接口设计。
- **新增套餐**：`SetmealDTO` 携带套餐基本信息 + 关联菜品列表 `List<SetmealDish>`，在事务中同时插入套餐表和套餐菜品关系表。
- **套餐分页查询**：多条件（名称、分类、状态）+ PageHelper + 动态 SQL，套餐数据关联分类名称与图片，返回 `SetmealPageQueryVO`。
- **删除套餐（批量）**：同样存在业务规则校验——**起售中的套餐不能删除**，删除套餐的同时删除套餐菜品关系表中的关联数据。
- **修改套餐**：查询回显（含关联菜品）→ 先删关系表再重新插入 → 更新套餐基本信息。
- **起售停售套餐**：起售前校验套餐内**所有菜品都必须处于起售状态**，否则抛 `SetmealEnableFailedException` 拒绝起售——这条规则在需求分析时很容易遗漏，是本次实战最有价值的收获之一。

整个实战走完了"需求分析 → 接口设计 → 代码实现 → Swagger 测试 → 前后端联调"的完整流程，是对前三周所学（三层架构、MyBatis、动态 SQL、事务、全局异常处理）的一次综合检验。

### 2.3 Day5 Redis 与店铺营业状态

- **Redis 入门**：理解 Redis 作为基于内存的键值型 NoSQL 数据库的特点——单线程模型 + IO 多路复用带来极高的读写吞吐，适合缓存、计数等高频读写场景。完成了本地安装与服务的启动、停止，掌握了 redis-server / redis-cli 的基本用法。
- **五种数据类型**：string（字符串）、hash（哈希）、list（列表）、set（无序集合）、zset（有序集合），并对照各自使用场景理解选型依据。
- **常用命令**：
    - string：`SET` / `GET` / `INCR` / `DECR` / `EXPIRE`（设置过期时间）
    - hash：`HSET` / `HGET` / `HGETALL` / `HDEL`
    - list：`LPUSH` / `RPUSH` / `LPOP` / `RPOP` / `LLEN`
    - set：`SADD` / `SMEMBERS` / `SISMEMBER` / `SCARD`
    - zset：`ZADD` / `ZRANGE` / `ZREVRANGE` / `ZREM`
    - 通用命令：`KEYS` / `EXISTS` / `DEL` / `TYPE` / `TTL`
- **Spring Data Redis**：引入 `spring-boot-starter-data-redis` 依赖，配置 `RedisTemplate` 及序列化器，通过 `ValueOperations` / `HashOperations` 等操作对象读写各类型数据，编写单元测试验证存取正确性。
- **店铺营业状态设置（综合应用）**：基于 Redis 的 string 类型存储营业状态（`1` 营业 / `0` 打烊），管理端提供设置与查询接口（`/admin/shop`），用户端提供查询接口（`/user/shop`）。与存入数据库的方案对比，理解了"营业状态"这类高频读取、低一致性要求的数据更适合放在 Redis。

### 2.4 Day6 HttpClient、微信小程序与微信登录

- **HttpClient**：学习了在 Java 代码中发送 HTTP 请求的 HttpClient 工具（GET / POST），理解了它在"后端调用第三方接口"场景下的价值，为微信登录中调用微信接口做准备。
- **微信小程序开发**：安装微信开发者工具，了解了小程序的项目结构（pages、app.json、wxml / wxss / js）、开发调试流程与代码上传发布的基本流程，通过入门案例在模拟器中跑通了第一个小程序页面。
- **微信登录（重点）**：
    - 完整流程：小程序端 `wx.login()` 获取临时凭证 code → 后端通过 HttpClient 调用微信接口 `jscode2session`（携带 appid、secret、js_code）换取 openid → 根据 openid 查询用户表，不存在则自动注册 → 登录成功签发 JWT 返回小程序端。
    - 后端实现：`WeChatProperties` 配置类管理 appid / secret；`HttpClientUtil` 发起请求并解析响应；`UserLoginDTO` 接收 code，`UserLoginVO` 返回用户信息与令牌；新增 C 端拦截器 `JwtTokenUserInterceptor`，通过 `excludePathPatterns` 放行登录接口，其余 `/user/**` 请求校验 JWT，并借助 ThreadLocal（`BaseContext`）保存当前登录用户 id。
- **商品浏览**：导入并通读了用户端分类浏览、菜品浏览（含口味）、套餐浏览的代码，理解 C 端接口与 B 端接口共用一个后端、按 `/admin` 与 `/user` 前缀区分并挂不同拦截器的设计思路。

## 四、问题与解决方案

| 问题 | 解决方案 |
|------|----------|
| 公共字段自动填充不生效，insert 后 create_time 仍为 NULL | 检查切面的切入点表达式是否匹配到 Mapper 方法、方法上是否标注了 `@AutoFill`，并核对反射设置的字段名（`AutoFillConstant` 常量）与实体属性保持一致 |
| 新增菜品时菜品插入成功但口味列表插入失败，数据不一致 | 在 Service 层方法上添加 `@Transactional`，使菜品与口味、套餐与关联菜品的多表操作同生共死 |
| 删除菜品时把被套餐关联的菜品也删掉了 | 删除前先查询 setmeal_dish 关联表，存在关联时抛 `DeletionNotAllowedException`，由全局异常处理器统一返回"存在关联套餐，无法删除" |
| 套餐起售时未校验内部菜品状态，停售菜品也能随套餐起售 | 起售前遍历套餐关联菜品，校验全部处于起售状态，否则抛 `SetmealEnableFailedException` 拒绝起售 |
| Redis 中 key 出现 `\xAC\xED\x00\x05` 等乱码前缀 | `RedisTemplate` 默认使用 JDK 序列化，配置 key 与 value 的 `StringRedisSerializer` 解决；纯字符串场景直接改用 `StringRedisTemplate` |
| 连接 Redis 报 Connection refused | 确认 redis-server 服务已启动、监听默认端口 6379，且连接配置的 host / port 正确 |
| 微信登录时 code2session 返回 errcode 错误码 | 核对 `WeChatProperties` 中的 appid / secret 是否与小程序后台一致；code 是一次性凭证，用后即失效，需重新调用 `wx.login()` 获取 |
| 小程序请求后端接口报"域名不合法" | 开发阶段在微信开发者工具中勾选"不校验合法域名"，上线前需配置 HTTPS 域名并添加到小程序后台的 request 合法域名列表 |

## 六、总结与思考

本周是从 B 端管理后台正式迈入 C 端用户端的转折点，四天内容各有侧重，收获很大：

- **AOP 知识在项目中真正"落地"了**：上周学 AOP 时写的操作日志案例还偏"玩具"，本周的公共字段自动填充直接就是生产级写法——自定义注解 + 切入点 + 环绕通知 + 反射 + ThreadLocal，一个功能同时用上了五大知识点。先学原理、再在项目里见到应用，这种"回环"式的体验让人非常踏实。

- **项目实战日逼出了"设计"能力**：Day4 套餐管理没有任何讲解，必须自己从产品原型出发分析业务规则、设计接口、梳理表关系。动手前觉得"照着写都会，自己设计没底"，做完后才发现，套餐管理几乎是菜品管理的复刻，真正难的从来不是写代码，而是需求分析时能不能把业务规则想全——比如"套餐起售必须校验菜品状态"这条规则，漏掉就是线上 bug。

- **Redis 与 MySQL 是互补而非替代**：学完 Redis 后最大的感受是"选型要看场景"——营业状态这类高频读取、低一致性要求的数据放 Redis，订单这类强一致性的核心数据放 MySQL。技术没有好坏，只有合不合适。

- **第三方登录是一条通用套路**：微信登录走通之后，理解了所有第三方登录的本质：客户端拿临时凭证 → 后端换取用户唯一标识 → 查库注册/登录 → 签发自己的令牌。以后接 QQ、钉钉、GitHub 登录，流程都是一样的，只是换接口而已。

- **多端共用一个后端的设计值得品味**：B 端（Web）和 C 端（小程序）访问同一个 SpringBoot 工程，靠 `/admin` 与 `/user` 前缀加两套拦截器实现权限隔离，既避免了重复开发，又保证了安全边界。

六周下来，从 Java SE 一路学到企业级项目的 C 端开发，学习节奏保持稳定。下周进入点餐业务核心（缓存、购物车、下单支付），继续加油。
