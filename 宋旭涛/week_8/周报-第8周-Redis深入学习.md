## 二、核心学习内容

### 2.1 Redis 高性能的原因
- **纯内存操作**：数据读写都在内存完成，避免了磁盘 IO 这一最大的性能瓶颈。
- **单线程执行命令**：避免了多线程的锁竞争与线程上下文切换开销（网络 IO 由 IO 多路复用处理，不占用命令执行线程）。
- **IO 多路复用**：基于 epoll 用少量线程管理海量连接。
- **高效的数据结构**：如 zset 使用跳表、hash 使用渐进式 rehash，保证单次操作的时间复杂度可控。

### 2.2 五种数据类型与典型应用场景
| 类型 | 说明 | 典型场景 |
| --- | --- | --- |
| `string` | 最基本的类型，可存文本、数字、二进制 | 对象缓存、计数器、分布式锁 |
| `hash` | 键值对集合，适合存对象 | 存储用户信息、购物车 |
| `list` | 双向链表，支持两端插入弹出 | 消息队列、最新列表 |
| `set` | 无序不重复集合，支持交并差运算 | 去重、共同好友、标签 |
| `sorted set` | 有序集合，元素关联 score 并按其排序 | 排行榜、延时队列 |

### 2.3 缓存三大问题与解决方案
- **缓存穿透**：查询根本不存在的数据，缓存永远不命中，请求全部打到数据库。
  1. 缓存空值：查不到也写入一个空值并设置较短 TTL（如 2 分钟）。
  2. 布隆过滤器：在缓存之前用位数组提前拦截不存在的 key。
- **缓存击穿**：某个热点 key 过期的一瞬间，大量并发请求同时打到数据库。
  1. 互斥锁 + 双重检查：只允许一个线程查库并重建缓存，其余线程短暂等待后重试。
  2. 逻辑过期：value 中额外存一个过期时间字段，读到逻辑过期时异步重建，读取线程不阻塞。
- **缓存雪崩**：大量 key 在同一时刻过期，或 Redis 整体宕机。
  1. 给 TTL 加随机值，把过期时间打散。
  2. 用主从 + 哨兵 / 集群保证 Redis 高可用。
  3. 服务端做限流与降级，避免数据库被击垮。

### 2.4 缓存与数据库的一致性策略
- **采用 Cache Aside 模式**：更新数据时**先更新数据库，再删除缓存**。
- **为什么"删除"而不是"更新"**：并发写场景下更新缓存容易让旧值覆盖新值；删除更简单，且下次读取时按需加载。
- **为什么"先更新库再删缓存"**：若先删缓存再更新库，删除后到更新完成之间的读请求会把旧数据重新加载进缓存，导致长期不一致。
- **延迟双删**：更新数据库后删除缓存，延迟一段时间（如 500ms）再删一次，用于兜住主从复制延迟带来的脏数据回填。
- **结论**：缓存方案只能保证最终一致，无法保证强一致；对一致性要求极高的数据应直接读库。

### 2.5 持久化机制
- **RDB**：按规则定时生成数据快照。文件小、恢复快，但两次快照之间的数据可能丢失。
- **AOF**：以追加方式记录写命令。数据更安全，但文件体积大、恢复速度慢；`appendfsync` 可选 `always` / `everysec` / `no`。
- **实践**：生产环境通常两者同时开启（混合持久化），兼顾恢复速度与数据安全。

### 2.6 过期删除与内存淘汰
- **过期删除策略**：惰性删除（访问时判断是否过期）+ 定期删除（周期性随机抽查一部分 key）。
- **八种内存淘汰策略**：`noeviction`、`allkeys-lru`、`allkeys-lfu`、`allkeys-random`、`volatile-lru`、`volatile-lfu`、`volatile-random`、`volatile-ttl`。
- **选择建议**：纯缓存场景推荐 `allkeys-lru`；若 Redis 中同时存放不能丢失的数据，则用 `volatile-*` 系列，只淘汰设置了过期时间的 key。

### 2.7 分布式锁的演进过程
1. **`SETNX` + `EXPIRE`**：两条命令不是原子操作，中间宕机会导致锁无法释放（死锁）。
2. **`SET key value NX EX seconds`**：一条命令原子地完成"设置 + 过期"，解决死锁问题。
3. **value 存唯一标识**（UUID + 线程 ID）：删除前先校验持有者，解决"误删他人锁"的问题。
4. **Lua 脚本**：把"校验 + 删除"合成原子操作，解决校验通过后、删除前锁刚好过期被他人获取的极端情况。
5. **Redisson 看门狗**：业务执行时间超过锁过期时间时自动续期，避免业务未完成锁就被释放。
- **补充**：主从架构下若主节点写入锁后尚未同步即宕机，锁可能丢失；Redisson 提供 RedLock 方案，但其正确性在业界仍有争议。

### 2.8 Spring Data Redis 实践要点
- `RedisTemplate` 默认使用 JDK 序列化，写入 Redis 的内容是可读性差、体积大的二进制流。
- 应配置 `StringRedisSerializer` 处理 key，`GenericJackson2JsonRedisSerializer` 处理 value，使数据以可读 JSON 形式存储。

### 2.9 面试八股复习：Java 基础与 MySQL
- **`==` 与 `equals`**：`==` 比较基本类型的值或引用地址；`equals` 默认比较引用，String、包装类等重写为比较内容。
- **String 常量池**：字面量方式创建会复用常量池中的对象；`new String()` 会在堆中额外创建对象。
- **HashMap 底层**：数组 + 链表 + 红黑树；默认容量 16、负载因子 0.75；链表长度达到 8 且数组容量达到 64 时转红黑树，否则优先扩容；正确性依赖 `hashCode` 与 `equals` 的契约。
- **ThreadLocal**：实现线程隔离，但线程池复用线程时会导致数据串号与内存泄漏，必须在请求结束（拦截器 `afterCompletion`）时调用 `remove()`。
- **MySQL 索引**：底层为 B+ 树，结构"矮胖"，3~4 层即可支撑千万级数据，显著减少磁盘 IO 次数。
- **索引失效场景**：不满足最左前缀、以 `%` 开头的 LIKE、对索引列做运算或使用函数、隐式类型转换、OR 连接了非索引列。
- **事务与隔离级别**：ACID 四大特性；MySQL 默认可重复读，通过 MVCC 解决不可重复读，配合间隙锁解决幻读。

## 四、问题与解决方案

| 问题 | 解决方案 |
| --- | --- |
| Redis 中存储的中文显示为乱码 | `RedisTemplate` 默认使用 JDK 序列化，改用 `StringRedisSerializer` 处理 key、`GenericJackson2JsonRedisSerializer` 处理 value |
| 查询不存在的 id 时，请求每次都打到数据库 | 缓存空值并设置较短 TTL（如 2 分钟），或引入布隆过滤器提前拦截 |
| 热点 key 过期瞬间大量并发请求压到数据库 | 采用互斥锁 + 双重检查：只允许一个线程查库重建缓存，其余线程等待后重试 |
| 业务还未执行完，分布式锁就已过期释放 | 设置合理的过期时间，或使用 Redisson 看门狗机制自动续期 |
| 手写分布式锁时误删了其他线程持有的锁 | value 存唯一标识并在删除前比对，同时用 Lua 脚本保证"校验 + 删除"的原子性 |
| 缓存与数据库数据不一致 | 采用 Cache Aside 模式：先更新数据库再删除缓存，必要时延迟双删兜底 |

## 六、总结与思考

本周最大的收获，是把"会用 Redis"推进到了"知道它为什么这么用"。缓存三大问题看起来是三个技巧，本质上都在回答同一个问题——**当缓存挡不住流量时，如何保证数据库不被打垮**；而缓存一致性方案则说明，引入缓存本质上是用"最终一致"换取"高性能"，这个取舍必须在设计阶段就想清楚，而不是出问题后再补救。

分布式锁的演进过程也让我印象深刻：从 `SETNX + EXPIRE` 到 `SET NX EX`，再到唯一标识、Lua 脚本、看门狗，每一步都是在修补上一步暴露出的边界问题。这让我理解了企业级方案往往不是一次设计出来的，而是被真实故障"逼"出来的。下周将把重心转向持久层的 MyBatis-Plus，继续用项目驱动的方式补齐技术栈。
