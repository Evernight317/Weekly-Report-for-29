## 二、核心学习内容

### 2.1 RAG 的整体流程
- **离线索引**：文档解析清洗 → 分块 → 向量化 → 写入向量库。
- **在线问答**：Query 向量化 → Top-K 检索 → 拼 Prompt → 大模型生成。
- 数据清洗这一步容易被跳过，但实际很影响效果：PDF 抽出来的文本里混着页眉页脚、换行断词、全半角不统一，不先规范化，后面分块和向量化都会受影响。

### 2.2 simple_rag 的实现
按模块拆开写，最后由 `pipeline.py` 统一编排：

| 模块 | 作用 |
| --- | --- |
| `document_parser` | 多格式解析 + 清洗噪声字符 |
| `chunker` | 固定窗口分块，size=500、overlap=50 |
| `embedder` | 本地 SentenceTransformer 推理，模型 BAAI/bge-small-zh-v1.5，输出 512 维、已做 L2 归一化 |
| `vector_store` | FAISS `IndexFlatIP` 写入与持久化（faiss.index / chunks.pkl / meta.json） |
| `retriever` | Top-K 召回 + MMR 去冗余 |
| `generator` | 拼装 Prompt 调 DeepSeek 生成答案 |

几个当时做决策的点：
- **向量库选 FAISS `IndexFlatIP`**：数据规模小，精确检索就够，不需要调参。
- **相似度用余弦**：L2 归一化之后内积就等于余弦相似度，正好是 `IndexFlatIP` 原生支持的计算方式，不用自己再算。
- **Embedding 用本地的 bge-small-zh-v1.5**：不依赖 API Key，跑起来没有额外成本。
- **分块用固定窗口 + 重叠**：最简单可靠，overlap 用来保住块与块之间的上下文衔接。

### 2.3 RAG 的常见优化手段（暂时只理解思路）
- **Parent-Child Chunking**：把文档按大块（parent）切一次，parent 内部再切成小块（child）存向量库，child 上带 `parent_id`；命中 child 后通过 `parent_id` 把整段 parent 取回来送模型。好处是召回粒度细、送进模型的上下文完整；代价是送的内容变多，token 更贵。
- **分片工具**：LangChain 的 Text Splitter，RAG 场景一般首选递归多级分割（按段落 → 句子 → 字符逐级降级）。
- **混合检索**：纯语义检索对专有名词、编号这类词不敏感，需要再加一路 BM25 做关键词精确匹配。两路结果可以归一化后按权重加权求和取 Top-K，也可以直接用 **RRF**——RRF 不看原始分数只看排名，对两路分数量纲不一致的情况更稳。
- **Bi-Encoder 与 Cross-Encoder**：Bi-Encoder 把问题和语料分开编码，语料可以离线建好索引、线上只算 query 向量，速度快；Cross-Encoder 把 query 和文档一起送进模型打分，准但慢，所以一般只在 Bi-Encoder 粗筛出的 Top-K 上做第二次精排。
- **MMR 去冗余**：循环 K 次，每次挑“和问题相关、同时和已选片段又不太像”的片段，避免 Top-K 里全是同一段话的重复表述。
- **GraphRAG**：把文档抽成实体关系图再检索，对多跳问题、需要跨 chunk 串联信息的情况有优势；缺点是构图要靠 LLM 处理，成本明显更高。

### 2.4 Spring AI 侧的对照
- **准备三步**：引依赖 → 配置模型 → 配置客户端，客户端可以在配置类里创建；阻塞调用用 `call()`，流式用 `stream()`。
- **Advisor**：Spring AI 用 AOP 的方式在会话调用链上做拦截和增强，会话日志、会话记忆都属于这一类，配置也挂在客户端上。
- **会话记忆**：按 system / user / assistant 的顺序维护一个消息数组，每轮往后追加，最后整体发给模型，靠这个实现“记得上文”。落地分三步：定义存储方式（默认内存）、注册 `MessageWindowChatMemory` Bean 并设 `maxMessages(20)`、在 prompt 后面挂 `ChatMemory.CONVERSATION_ID` 区分会话。存储介质可以自己换（内存或 MySQL）。
- **Function Calling**：Spring AI 把协议层封装好了，我们只需要写 Tool 的配置；`description` 写得好不好，直接决定模型判断该不该用这个工具。
- **向量检索**：用 `EmbeddingModel` 做向量化，`VectorStore` 做存储和检索。实际代码里用 `PagePdfDocumentReader` 按页读 PDF（`withPagesPerDocument(1)`，一页一个 Document），写库后通过 `SearchRequest` 检索，可以设 `topK`、`similarityThreshold`，还可以用 `filterExpression` 按 `file_name` 之类的元数据过滤。
- **提示词工程**六条：指令清晰、用分隔符标记输入、复杂任务按步骤拆解、给输入输出示例、明确输出格式、设定角色。
- 对照下来比较清楚的一点：Spring AI 省掉的是装配和样板代码，`chunk → embed → Top-K → 拼 Prompt` 这条链路本身一步都没少。

## 四、问题与解决方案

| 问题 | 解决方案 |
| --- | --- |
| FAISS 返回的分数看着不对劲，不同长度的文本没法横向比 | 用的是 `IndexFlatIP`（内积），向量必须先 L2 归一化内积才等于余弦相似度；在 embedding 时就设 `normalize_embeddings=True` |
| 检索到的片段经常只有半句话，答案被切断 | overlap 设得太小，调到 50；同时也意识到纯固定窗口不适合长文档，后面想试 Parent-Child 分块 |
| PDF 一页一个 Document，单块内容太长，检索粒度太粗 | 一页一个 Document 只是最省事的做法，页内还得再按段落二次分块，否则检索命中的块动辄上千字 |
| 一开始把余弦距离和余弦相似度搞混，以为“距离越大越相似” | 明确区分：欧氏距离越小越相似，余弦相似度（夹角）越大越相似；代码里统一按余弦相似度判断 |
| 专有名词、编号类的内容检索召不回来 | 这是纯向量检索的通病，需要补 BM25 那一路关键词检索，目前只记了方案，还没实现 |
| Spring AI 流式输出前端显示乱码 | Controller 上要声明 `produces = "text/html;charset=UTF-8"` |
| 多轮对话聊十几轮之后模型就“忘”了前面的约束 | `maxMessages` 截断导致早期消息被丢掉，调到 20，并把关键约束移到 system 里，避免被窗口挤出去 |
