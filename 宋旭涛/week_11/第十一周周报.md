## 二、核心学习内容

### 2.1 Function Calling：Agent 的地基
- Agent 与传统对话最大的区别是**能调工具**，而工具调用的入口就是 Function Calling：模型不执行函数，只输出"要调哪个工具、参数是什么"，真正执行和结果回填由程序完成。
- **Tool 的 `description` 极其关键**，它是模型判断"该不该用这个工具"的唯一依据，写得含糊就会出现该调不调、乱调的问题。
- 工程上的分层很清晰：`tools`（工具定义与实现）→ `llm`（模型客户端封装）→ `agent`（循环与提示词），这一层拆分在后面所有范式里都复用。

### 2.2 Agent 的五种基本范式
- **ReAct**：`Thought → Action → Observation` 单链循环，边想边做、每步依赖上一步的观察结果，适合路径不确定、需要频繁与环境交互的任务。
- **Plan-and-Execute**：先一次性产出全局计划，再逐步执行，某步失败可以局部重规划，适合步骤大体可预判、长流程的任务；代价是计划本身可能一开始就跑偏。
- **Reflexion**：执行 → 评估 → 写出"反思" → 带着反思重试，反思结果作为策略记忆跨轮复用，本质是用自然语言做梯度更新。
- **LATS / MCTS**：把决策展开成树，用 UCB 平衡探索与利用，多条路径并行试探后回溯选优，效果上限高但 token 成本明显上升。
- **Multi-Agent Crew**：多个角色（研究 / 撰写 / 审稿）共享同一个 thread，靠角色分工与消息传递完成单 Agent 难以拆解的任务。
- **选型判断**：路径不确定用 ReAct，流程可预判用 Plan-and-Execute，对结果质量要求高用 Reflexion / LATS，任务本身可切分为不同专业视角时上多 Agent。

### 2.3 RAG 的完整链路
- **离线索引**：文档解析清洗 → 分块 → 向量化 → 写入向量库并持久化。
- **在线问答**：Query 向量化 → Top-K 检索 → （可选）去冗余 / 重排 → 拼装 Prompt → 大模型生成。
- **分块策略**：固定窗口 + 重叠是最可靠的起点；进一步可用 Parent-Child Chunking——child 入库并带上 `parent_id`，命中 child 后再回取整段 parent 送模型，召回精度与上下文完整性能兼顾，代价是送入的 token 变多。
- **检索不止语义**：纯向量检索对专有名词、编号、代码标识符不敏感，需要配合 BM25 做关键词精确匹配。两路结果可以归一化后加权融合，也可以直接用 **RRF** 按排名融合（不看原始分数，只看名次），后者对分数量纲不一致更鲁棒。
- **两阶段排序**：Bi-Encoder 把查询和语料分别编码，可离线建索引、线上只算 query 向量，快；Cross-Encoder 把 query 和文档拼在一起送模型打分，准但慢，通常只在粗筛后的 Top-K 上做精排。
- **MMR 去冗余**：每轮选"与问题相关、且与已选片段不相似"的片段，避免 Top-K 全是同一段话的重复表述。
- **GraphRAG**：先把文档抽成实体关系图，检索时沿图做多跳扩展，天然适合"跨章节、需要串联多处信息"的问题，但构图依赖 LLM，成本高，属于进阶方案。

### 2.4 动手实现最小 RAG 闭环
- 不依赖 LangChain，纯 Python 拆分模块：`document_parser` / `chunker` / `embedder` / `vector_store` / `retriever` / `generator`，由 `pipeline` 统一编排 `build_index()` 与 `ask()` 两个入口。
- 向量化用本地 **BAAI/bge-small-zh-v1.5**（SentenceTransformer，无需 API Key），向量库用 **FAISS IndexFlatIP**，生成用 deepseek-chat。
- **关键细节**：IndexFlatIP 算的是内积，必须对向量做 L2 归一化，内积才等价于余弦相似度，否则不同长度文本的分数不可比；分块参数取 `size=500 / overlap=50`。
- 生产化方向记了几条：按文件哈希做嵌入缓存、增量更新只重建变更块、十万块以上换 `IndexIVFFlat` / `HNSW`、加 BM25 做混合检索、加 `bge-reranker` 精排。

### 2.5 记忆机制
- **窗口记忆**：只保留最近 N 轮，简单但会硬截断早期信息。
- **摘要记忆**：旧对话压缩成摘要，把"细节"换成"梗概"，控制上下文长度。
- **长期记忆**：把事实抽出来存外部存储，按需检索召回（Mem0 那套思路）。
- **三因子打分**：召回时综合相关性、时效性、重要性排序，而不是只看相似度。

### 2.6 模型路由与工程化
- 一条完整的调用链应当是 **路由 → 熔断 → 重试 → 降级 → 计费** 闭环，而不是直接裸调 API。
- **熔断器**三态：Closed / Open / Half-Open，Half-Open 用小流量探测恢复，避免故障时反复打满下游。
- **可观测性**：Trace 里要区分 route / llm / tool / cache / breaker / retry / fallback / billing 这些 Span，出问题才能定位到具体环节。
- **缓存风险**：L1/L2 双层缓存能省成本，但语义缓存存在"表述相近、意图不同"的误命中，只能用在幂等、低风险的查询上。
- **幻觉治理**分三段：事前靠 RAG grounding 把答案约束在资料内，事中靠引用与拒答，事后靠反馈与审计。

### 2.7 Harness 与 Loop Engineering
- **Harness** 指的是围绕模型的工程外壳：`CLAUDE.md` 提供项目上下文、`skills` 提供可复用流程（plan / implement / validate）、plans 与 reports 落盘形成可追溯的工件。同一条模型，harness 不同，产出质量差别很大。
- **Loop Engineering** 的核心主张：不要再不停地手动 prompt agent，而要设计"会去 prompt agent 的 loop"——人只定义目标与停机条件，由 orchestrator 根据状态持续发起下一轮。人的职责没有消失，而是上移了一层。

### 2.8 开源 Agent 源码精读
- **Hermes**：从 memory、run-agent 主循环、eval、prompt、环境注入几个章节建立 Runtime 心智模型，理解了"一个 Agent 进程到底在循环什么"。
- **Pi**：Core / Interactive 分层、会话树（sessions）、event bus 的 emit / subscribe、agent-loop 的 stop 与 fallback、compaction（上下文压缩）触发时机，对"多轮长会话怎么不炸上下文"有了具体答案。
- 对照精简版 **waku** 看 Harness · Loop · Memory · Eval 四支柱的最小实现，再回头看完整项目就不容易被工程细节淹没。

### 2.9 从"读"到"设计"：把模式落进自己的框架
- 在学完上述范式后，开始设计自己的竞标式多智能体框架 ContractNet，把学到的模式对应到具体模块：

| 模块 | 职责 | 对应的已学模式 |
| --- | --- | --- |
| Planner | 把任务分解成可竞标的子任务 | Plan-and-Execute 的规划阶段 |
| Auctioneer | 收集报价、按能力与成本选标 | 多 Agent 协作中的任务分配 |
| Orchestrator | 调度主循环、推进任务状态机 | ReAct 的循环骨架 + Loop Engineering |
| Quality Gate | 产物验收，不达标打回重做 | Reflexion 的评估与重试 |
| Conflict Resolver | 多 Agent 结论冲突时裁决 | 多 Agent 架构中的仲裁机制 |
| State Store / Memory | 全局状态与 Agent 局部记忆分离 | 窗口记忆 + 长期记忆 |
| Tool Sandbox | 工具白名单、参数校验、审计 | Function Calling 的权限分层 |
| Observability / Eval | 全链路 Trace 与效果评估 | 模型路由里的可观测性与 RAG 评测 |

- 设计过程中最大的收获是：**范式不是拿来炫技的，而是要在正确的层级上被复用**——同一个"评估-重试"在单 Agent 里是 Reflexion，在框架里就变成了 Quality Gate。

### 2.10 Java 侧对照：Spring AI
- Spring AI 的使用准备就三步：引依赖 → 配置模型 → 配置客户端；`call()` 阻塞、`stream()` 流式。
- **Advisor** 机制本质是 AOP：在调用链上做拦截与增强，会话记忆、日志都属于这一类。
- **会话记忆**的实现思路：按 system / user / assistant 的顺序维护消息数组，每次把历史一起送模型；用 `MessageWindowChatMemory` 限制最大消息数，通过 `ChatMemory.CONVERSATION_ID` 区分会话，存储介质可换（内存 / MySQL）。
- **RAG 侧**用 `EmbeddingModel` + `VectorStore`，`SearchRequest` 里可以设 `topK`、`similarityThreshold`、以及按 `file_name` 之类的元数据过滤，正好对应 Python 侧手写的那套 topK + 阈值 + 过滤逻辑。
- 对照之后更清楚：框架省掉的是装配和样板代码，`chunk → embed → topK → prompt` 这条链路本身一步都少不了。

## 四、问题与解决方案

| 问题 | 解决方案 |
| --- | --- |
| FAISS 检索分数看起来不合理，长短文本不可比 | 使用 `IndexFlatIP`（内积）时必须先做 L2 归一化，归一化后内积才等于余弦相似度 |
| 分块后答案经常"只答一半" | overlap 设得太小导致跨块语义被切断，改为 `overlap=50`，并对长文档改用 Parent-Child 分块回取整段 |
| 专有名词、接口名检索不出来 | 纯语义检索对精确词不敏感，补充 BM25 关键词召回，两路结果用 RRF 融合 |
| Top-K 结果高度重复，浪费上下文 | 加 MMR 去冗余，按"相关且互不相似"重新挑选 |
| 全量重建索引越来越慢 | 按文件哈希做嵌入缓存，仅对变更文件重新分块与向量化 |
| 多轮对话轮数一多就超上下文 | 改用窗口记忆 + 摘要记忆组合，只保留关键事实，早期内容压成摘要 |
| Spring AI 流式输出前端乱码 | 接口需声明 `produces = "text/html;charset=UTF-8"` |
| 会话记忆偶尔"忘事" | `maxMessages` 截断过狠，调到 20 并把关键约束放进 system 提示词 |
| 多 Agent 各角色结论互相冲突，无法收敛 | 在框架里单独设 Conflict Resolver 与 Quality Gate，用规则 + 复评做裁决，而不是让角色互相说服 |

## 六、总结与思考

这周最大的变化是**视角的切换**。之前学 Agent，关注的是"怎么让模型调通一个工具"；这周把几种范式横向摆开对比之后才发现，ReAct、Plan-and-Execute、Reflexion、LATS 之间的差别，本质不是提示词技巧的差别，而是**在什么层级做决策**的差别：ReAct 把决策放在每一步，Plan-and-Execute 放在开头，LATS 把它展开成一棵树。想清楚这一点，选型就不用背结论了。

第二个体会来自 RAG。真正跑通一个最小闭环只花了一天，但要让它"答得准"却是另一回事——分块、归一化、混合检索、重排、去冗余，每一步都在解决一个具体的失效模式。尤其是"IndexFlatIP 必须先归一化"这种细节，看文档时完全不会在意，只有分数不对劲时才会去查，这类知识必须靠动手才能沉淀下来。

最后是把学到的东西用起来。设计 ContractNet 的时候我才发现，前面读的那些范式其实就是零件：Reflexion 放在框架里就是 Quality Gate，ReAct 的循环骨架放在 orchestrator 里就是主调度。**学过和能设计之间的差距，就是有没有把这些零件重新组装过一遍**。下周准备先让最小版本跑起来，用真实任务检验这套竞标机制到底站不站得住。
