## 二、核心学习内容

### 2.1 MySQL 锁（承接上周）

- 重点梳理了行锁、表锁、间隙锁与临键锁的关系，以及 RR 隔离级别下间隙锁如何配合 MVCC 堵住幻读。

### 2.2 Docker：容器化与环境一致性

- **镜像与容器**：镜像是由 Dockerfile 逐层叠加的只读多层结构，容器 = 镜像 + 一层可写层；同层可在多个镜像间共享，构建时未变化的层直接命中缓存，这也是"先 COPY 依赖描述文件、再 COPY 源码"能显著加速构建的原因。
- **隔离原理**：依靠 Linux 的 **Namespace**（隔离"看得见什么"）和 **Cgroups**（限制"用多少"），容器与宿主机**共享内核**，所以体积是 MB 级、启动是秒级，隔离强度弱于虚拟机。
- **数据持久化**：容器可写层随容器删除而消失，数据库这类数据必须挂**命名卷**；配置文件用 **bind mount**。之所以数据库不用 bind mount，是因为宿主机的目录权限会直接带进容器，容易出现初始化失败。
- **Dockerfile 生产化**：多阶段构建（构建阶段带 Maven，运行阶段只留 JRE + jar）、基础镜像换 `alpine`、非 root 用户运行、补 `.dockerignore`、`ENTRYPOINT` 用 exec 数组形式（shell 形式会让 java 变成 PID 1 的子进程，收不到 `SIGTERM`，优雅停机失效）。
- **Compose 编排**：`depends_on` 只保证启动顺序，**不保证依赖已就绪**，必须配 `healthcheck` + `condition: service_healthy`；容器间通过**自定义网络的内嵌 DNS** 用服务名互访。

### 2.3 Nginx：接入层与反向代理

- **多进程模型**：master 负责读配置、管理 worker，**不接收请求**；worker 相互独立、各自监听同一端口，由内核分配连接。`worker_processes` 一般等于 CPU 核数；`worker_connections` 是**单个 worker** 的上限，总上限为两者相乘，**做反向代理时要再除以 2**（一个请求同时占用客户端和后端两个连接）。
- **零拷贝**：`sendfile` 省掉的是"内核态 → 用户态 → 内核态"的两次拷贝和四次切换，数据仍然经过内核页缓存，并不是"不经过内存"。
- **虚拟主机**：nginx 靠 HTTP 请求头里的 **`Host`** 匹配 `server_name`，而不是自己去解析域名；匹配优先级为**精确 → 通配符（长的优先）→ 正则 → `default_server`**。请求未带 `Host` 时走该端口的默认站点。
- **反向代理与负载均衡**：`upstream` 定义后端池，`weight` 是**相对权重不是百分比**；`ip_hash` 解决 session 问题，`least_conn` 适合长连接；开源版只有**被动健康检查**（`max_fails` / `fail_timeout`），主动探测是商业版能力。
- **`rewrite` 的四个 flag**：`last` 改写后**重新匹配 location**，`break` **留在当前 location**；`redirect` 返回 302（浏览器不缓存、SEO 保留原地址），`permanent` 返回 301（浏览器缓存、SEO 转移权重）。改写 URI 后还要用当前 location 的 `proxy_pass` 时必须用 `break`。
- **HTTPS**：**非对称加密负责安全地交换密钥和身份认证，对称加密负责传输业务数据**；证书的信任根是内置在系统里、不走网络传输的 CA 公钥。

### 2.4 MySQL 运维：日志与主从复制

- **binlog** 记录所有 DDL 与 DML，**不含查询语句**，是数据恢复和主从复制的基础；不配过期时间会把磁盘吃满。
- **主从三线程**：主库的 **Binlog Dump** 线程推送日志，从库的 **IO Thread** 写入 **relay log**，从库的 **SQL Thread** 重放。中间多一层 relay log 是为了把"接收"和"执行"解耦。
- **`binlog_format=ROW`**：按行记录变更，避免 `NOW()`、不带 `ORDER BY` 的 `LIMIT` 这类语句在主从执行结果不一致；代价是日志体积大。
- **GTID**：给每个事务一个全局唯一编号，配 `SOURCE_AUTO_POSITION=1` 后从库自动定位位点，不用手工记 binlog 文件名和偏移量。
- **读写分离**：主从是 AP 模型，异步复制带来**主从延迟**，"写后立刻读"的场景（支付后查订单、扣库存后查库存）必须强制走主库。

### 2.5 分库分表与 ShardingSphere

- **四种拆分**：垂直分库（按业务拆）、垂直分表（按字段冷热拆）、水平分库、水平分表。**垂直拆结构，水平拆数据。**
- **分片键的选择标准**：**分片键不是主键**，不要求唯一，真正的标准是"查询条件里最常出现、基数高、分布均匀"。电商订单表通常按 `user_id` 分片，因为"我的订单"查询频率最高。
- **分片算法**：`MOD` / `HASH_MOD` 分布均匀但**扩容要重算几乎全部数据**；`RANGE` / `INTERVAL` 扩容容易但有热点。`inline` 行表达式只支持数字后缀和简单取模，复杂逻辑（字符串前缀、租户路由、复合键）必须用 `CLASS_BASED` 自定义算法。
- **分布式主键**：水平分片后自增主键会冲突，用 `keyGenerateStrategy` 配 `SNOWFLAKE` 自动生成；雪花趋势递增、对 B+ 树友好，但要处理时钟回拨和 workerId 分配。
- **绑定表与广播表**：绑定表用于**分片键相同的关联表**（`t_order` 与 `t_order_item`），配置后 JOIN 只路由一个分片，否则会做笛卡尔积路由；广播表用于**每个分片都要存一份的小表**（字典表），代价是写操作要写所有分片。
- **跨分片查询的坑**：`LIMIT 100000, 10` 需要每个分片各取 100010 条再归并，必须改成游标分页；`AVG` 不能对各分片的平均值再求平均，要用总和除以总条数。
- **分布式事务**：`LOCAL` 各分片各自提交、跨库不回滚；`XA` 两阶段提交强一致，但 `prepare` 后行锁一直持有到 `commit`，性能差；`BASE`（Seata AT）一阶段提交本地事务、二阶段靠 undo log 补偿，是互联网主流方案。

### 2.6 Redis 高可用：主从、哨兵与分片集群

- **主从同步**：首次是全量同步，从库发 `psync ? -1` → 主库比对 `replid` → `fullresync` → 主库 `bgsave` 生成 RDB 传输 → 再把期间累积在 `repl_baklog` 的增量补发。为什么要用 RDB，是因为内存数据无法直接序列化传输，RDB 是紧凑的二进制快照。
- **`replid` 与 `offset`**：前者判断"是不是同一份数据集"，后者判断"落后多少字节"。`repl_baklog` 是**环形缓冲区**，写满会覆盖最早的记录，此时只能退化为全量同步。
- **哨兵**：**主观下线**是单个哨兵判断（可能被网络抖动误导），**客观下线**需要超过 `quorum` 个哨兵确认。选新主库的顺序是：先排除断开时间过长的从库 → 比较 `slave-priority` → 比较 `offset`（数据最新优先）→ 比较 `runid`。哨兵本身用 Raft 选 leader，需要部署奇数个。
- **分片集群**：16384 个槽是"心跳包大小"和"最大节点数"之间的折中——16384 个槽的位图是 2KB，65536 就是 8KB，心跳包会大四倍。槽位按 `CRC16(key) % 16384` 计算，key 里带 `{}` 时只有括号内的部分参与计算，这就是 **hash tag**，用来让多个 key 落到同一个槽，从而支持 `MGET`、事务和 Lua。
- **故障转移的两套机制**：主从+哨兵由**哨兵**判断并执行转移；分片集群由**集群内部**的 master 互相 ping、投票完成，不依赖哨兵。

### 2.7 Redis 持久化与多级缓存

- **RDB**：`bgsave` 通过 `fork` 子进程完成，子进程复制主进程的**页表**并依靠 **copy-on-write** 与主进程共享内存页。COW 对主进程是**完全透明**的，"写保护"只是内核用来触发复制的标记，主进程照常读写；RDB 丢数据的原因是它只是快照，两次快照之间的写入会丢，与只读无关。COW 的代价是写入频繁时内存可能接近翻倍。
- **AOF**：三种刷盘策略 `always` / `everysec` / `no`，生产用 `everysec`（最多丢 1 秒）。AOF 文件通常**比 RDB 大得多**，所以需要 `bgrewriteaof`——它不是压缩老文件，而是**直接读内存里的最终状态、用最少的命令重建**。
- **混合持久化**：AOF 文件前半段写 RDB 格式快照、后半段追加增量命令，兼得恢复速度与数据安全。
- **多级缓存**：浏览器 → Nginx（`lua_shared_dict` 让多 worker 共享缓存）→ Redis → Tomcat 本地缓存（Caffeine）。本地缓存是进程内的，必须用 `ip_hash` 保证同一用户固定落到同一台 Tomcat，否则每台都要查一次库，命中率接近 0，副作用是负载不均和扩缩容后大面积失效。
- **缓存同步**：`canal` 伪装成 MySQL 的从库订阅 binlog，业务零侵入，但有秒级延迟和额外运维成本，且要求 `binlog_format=ROW`。

## 四、问题与解决方案

| 问题 | 解决方案 |
| --- | --- |
| Docker 启动报端口已被占用，容器卡在 `Created` 状态、网络为空 | 端口映射在创建时写死且已停止的旧容器仍占用映射，用 `docker ps -a` 找到旧容器 `docker rm -f` 后重建 |
| 从库报 `Unknown MySQL server host 'mysql-master'` | 默认 bridge 网络不启用内嵌 DNS，建自定义网络后才能用容器名互访 |
| 从库容器里连主库写成 3307 连不上 | 容器之间走的是**容器端口 3306**，3307 只是宿主机映射出来的端口 |
| MySQL 8.0 建好复制账号后客户端连不上 | 默认认证插件是 `caching_sha2_password`，老客户端不支持，建号时指定 `mysql_native_password` 或升级驱动 |
| `docker compose up` 后应用启动即连库失败 | `depends_on` 只保证启动顺序不保证就绪，改为 `healthcheck` + `condition: service_healthy` |
| 从库被误写，导致主从中断 | `read_only` 对 root 无效，补上 `super_read_only=ON`，并收窄应用账号权限 |
| ShardingSphere 报 `Table "T_USER" not found` | 旧版配置前缀未生效 + 连到了依赖里的空 H2 + 从库 URL 把数据源名当成了库名，改用独立 YAML 配置并统一业务库名 |
| Redis `bgsave` 期间内存明显上涨 | COW 在写入时复制共享页，属正常现象，控制内存占用不超过物理内存的 50%~60% |
| 一直以为主从延迟可以用哨兵看 | 哨兵只管存活，延迟要看 `INFO replication` 里的 offset 差值和 `lag` |

## 六、总结与思考

这一周最直观的变化，是项目从"在我电脑上能跑"变成了"部署出去也能跑"。过程中遇到的问题几乎都不是业务代码的问题，而是环境问题：端口被旧容器占着、容器名解析不到、依赖的服务还没初始化完就先去连。以前觉得这些是"运维的事"，真正自己搭一遍才发现，它们本质上是**工程约束**——代码写对了不等于服务能用，中间还隔着一层环境与启动顺序。Docker 和 Compose 的价值就在于把这些约束变成可版本化、可复制的配置文件，而不是留在某个人的记忆里。

另一层收获是对"分布式要付代价"有了具体感知。分库分表看起来只是把数据拆开，但拆完立刻要面对跨库 JOIN、深分页、分布式主键和分布式事务；Redis 加了主从和集群，可用性上去了，但主从延迟、全量同步、槽位重分布这些问题也随之而来。每一个方案都不是"更好"，而是"用另一种代价换另一种收益"——取模分布均匀但扩容困难，范围分片扩容容易但有热点，XA 强一致但锁得久，Seata 性能好但要接受最终一致。选型时能不能说清代价，比记住方案本身更重要。
