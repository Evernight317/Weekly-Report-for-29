## 二、核心学习内容

### 2.1 为什么需要登录认证

HTTP 协议是**无状态**的——每次请求之间互相独立，服务器不记得上一次请求是谁发的。这就带来一个问题：

> 用户在登录页面输入账号密码成功登录后，下一次访问业务接口时，服务器怎么知道"这个人已经登录过了"？

**认证（Authentication）**：确认"你是谁"——验证用户名密码是否正确。
**授权（Authorization）**：确认"你能干什么"——判断用户是否有权限访问某个资源。

登录认证要解决的核心问题，就是把一次登录的结果"记住"，并在后续的每次请求中证明身份。

**核心特性**：
- **无状态协议**：HTTP 请求间默认无关联，需要借助会话技术维持登录态
- **认证与授权分离**：先认证身份，再判断权限
- **三种会话方案**：Cookie、Session、JWT，各有优缺点

### 2.2 Cookie（客户端会话技术）

Cookie 是**客户端**的会话技术：服务器在响应头中通过 `Set-Cookie` 写入数据，浏览器收到后自动保存，并在后续每次请求中通过 `Cookie` 请求头自动携带回服务器。

**登录成功后写入 Cookie**

```java
@RestController
public class LoginController {

    @PostMapping("/login")
    public Result login(String username, String password, HttpServletResponse response) {
        // 1. 校验账号密码
        if (!"admin".equals(username) || !"123456".equals(password)) {
            return Result.error("用户名或密码错误");
        }
        // 2. 登录成功，把用户信息写入 Cookie
        Cookie cookie = new Cookie("username", username);
        cookie.setMaxAge(60 * 60 * 24);      // 有效期：1 天（秒）
        cookie.setHttpOnly(true);            // 禁止 JS 读取，防止 XSS 窃取
        cookie.setPath("/");                 // 作用于整个站点
        response.addCookie(cookie);
        return Result.success("登录成功");
    }
}
```

**关键点说明**：
- `setMaxAge` 设置 Cookie 有效期，负数表示会话级（关闭浏览器失效），0 表示立即删除
- `setHttpOnly(true)` 后，`document.cookie` 无法读取该 Cookie，可防 XSS 攻击
- `setPath("/")` 指定 Cookie 的生效路径

**读取请求中携带的 Cookie**

```java
@GetMapping("/info")
public Result getInfo(HttpServletRequest request) {
    Cookie[] cookies = request.getCookies();
    if (cookies != null) {
        for (Cookie cookie : cookies) {
            if ("username".equals(cookie.getName())) {
                return Result.success("当前用户：" + cookie.getValue());
            }
        }
    }
    return Result.error("未登录");
}
```

**技术要点**：
- Cookie 大小限制约 **4KB**，只能存少量非敏感数据
- Cookie 存储在浏览器端，**明文可见**，不适合存放密码等敏感信息
- 手动解析 Cookie 比较繁琐，实际项目中常借助 Spring 的 `@CookieValue` 注解

### 2.3 Session（服务端会话技术）

Session 是**服务端**的会话技术：服务器为每个会话分配一个唯一的 **SessionId**，把用户数据保存在服务器内存中，SessionId 通过 Cookie（默认名 `JSESSIONID`）下发给浏览器。

**登录成功后写入 Session**

```java
@RestController
public class LoginController {

    @PostMapping("/login")
    public Result login(String username, String password, HttpSession session) {
        // 1. 校验账号密码
        if (!"admin".equals(username) || !"123456".equals(password)) {
            return Result.error("用户名或密码错误");
        }
        // 2. 登录成功，把用户信息存到 Session（服务端）
        session.setAttribute("username", username);
        return Result.success("登录成功");
    }
}
```

**从 Session 中读取用户**

```java
@GetMapping("/info")
public Result getInfo(HttpSession session) {
    // 从 Session 中取数据，无需再解析 Cookie
    Object username = session.getAttribute("username");
    if (username == null) {
        return Result.error("未登录");
    }
    return Result.success("当前用户：" + username);
}
```

**工作原理**：

1. 首次请求时，服务器创建 Session 对象并生成唯一 SessionId
2. 服务器通过 `Set-Cookie: JSESSIONID=xxx` 把 SessionId 下发给浏览器
3. 浏览器后续请求自动携带 `Cookie: JSESSIONID=xxx`
4. 服务器根据 SessionId 找到对应的 Session，从中读取用户数据

**关键点说明**：
- Session 数据存在**服务器内存**中，安全，但占用服务器资源
- 默认超时时间 30 分钟（Tomcat），超时后 Session 失效，需重新登录
- 多个服务器（集群）时，Session 不共享，需要做 Session 同步或改用分布式 Session（如 Redis）

### 2.4 Cookie 与 Session 对比

| 对比项     | Cookie                                  | Session                                      |
| ---------- | --------------------------------------- | -------------------------------------------- |
| 存储位置   | 客户端（浏览器）                        | 服务端（服务器内存）                         |
| 存储容量   | 约 4KB                                  | 理论上无限制（受服务器内存影响）             |
| 安全性     | 明文存储，易被窃取，相对不安全          | 数据在服务端，相对安全                       |
| 请求携带   | 每次请求自动携带，增加流量              | 只携带 SessionId，数据在服务端               |
| 分布式支持 | 天然支持（数据在客户端）                | 不共享，集群下需引入 Redis 等解决方案        |
| 典型场景   | 记住登录状态、购物车、用户偏好          | 登录态、权限数据、购物车等业务数据           |

**选型建议**：敏感数据放 **Session**（服务端），少量非敏感数据放 **Cookie**（客户端）。

### 2.5 JWT（JSON Web Token）

Session 方案在集群/分布式场景下需要额外共享 Session，且服务端要维护会话状态。**JWT** 是一种**无状态**的令牌方案：把用户信息经过签名后发放给客户端，服务端校验签名即可，无需存储会话数据。

**JWT 的结构**：由三部分组成，用 `.` 连接：

```
Header.Payload.Signature
```

- **Header**（头部）：声明签名算法，如 `{"alg": "HS256", "typ": "JWT"}`
- **Payload**（载荷）：存放业务数据，如用户 id、用户名、过期时间
- **Signature**（签名）：用密钥对 `Header.Payload` 做 HMAC 签名，防止数据被篡改

**JWT 工具类（生成与校验）**

```java
public class JwtUtils {

    private static final String SECRET_KEY = "mySecretKey123456";  // 签名密钥（生产环境放配置文件）
    private static final long EXPIRE_MS = 60 * 60 * 1000;          // 有效期 1 小时

    // 生成 JWT
    public static String generateToken(String username) {
        return Jwts.builder()
                .setSubject(username)                      // 主体，存用户名
                .setIssuedAt(new Date())                   // 签发时间
                .setExpiration(new Date(System.currentTimeMillis() + EXPIRE_MS)) // 过期时间
                .signWith(SignatureAlgorithm.HS256, SECRET_KEY)
                .compact();
    }

    // 校验 JWT，成功返回用户名，失败抛出异常
    public static String parseToken(String token) {
        Claims claims = Jwts.parser()
                .setSigningKey(SECRET_KEY)
                .parseClaimsJws(token)
                .getBody();
        return claims.getSubject();
    }
}
```

**登录后签发 JWT 返回给前端**

```java
@PostMapping("/login")
public Result login(String username, String password) {
    // 1. 校验账号密码
    if (!"admin".equals(username) || !"123456".equals(password)) {
        return Result.error("用户名或密码错误");
    }
    // 2. 签发 JWT
    String token = JwtUtils.generateToken(username);
    return Result.success(token);   // 前端保存 token，后续请求放入请求头
}
```

**关键点说明**：
- JWT 是**无状态**的，服务端不保存任何会话数据，天然支持分布式
- 前端拿到 token 后存储在 `localStorage`，后续请求通过 `Authorization: Bearer <token>` 请求头携带
- 缺点：签发后无法主动让 token 失效（除非加黑名单），有效期需要权衡设置
- Payload 只是 Base64 编码，**不是加密**，不能放密码等敏感信息

### 2.6 Filter 过滤器实现登录拦截

有了登录态（Session 或 JWT），还需要一个统一的入口去校验"每个请求是否已登录"。**Filter 过滤器**是 Servlet 规范提供的组件，可以拦截请求，在进入 Controller 之前做校验。

**自定义登录过滤器**

```java
@WebFilter(urlPatterns = "/*")   // 拦截所有请求
public class LoginFilter implements Filter {

    // 放行白名单：登录接口和静态资源不需要校验
    private static final List<String> WHITE_LIST = Arrays.asList(
            "/login", "/css/**", "/js/**", "/img/**"
    );

    @Override
    public void doFilter(ServletRequest servletRequest,
                         ServletResponse servletResponse,
                         FilterChain chain) throws IOException, ServletException {
        HttpServletRequest request = (HttpServletRequest) servletRequest;
        HttpServletResponse response = (HttpServletResponse) servletResponse;
        String uri = request.getRequestURI();

        // 1. 白名单直接放行
        if (WHITE_LIST.contains(uri)) {
            chain.doFilter(servletRequest, servletResponse);
            return;
        }

        // 2. 校验登录态（以 Session 为例）
        HttpSession session = request.getSession();
        if (session.getAttribute("username") != null) {
            // 已登录，放行
            chain.doFilter(servletRequest, servletResponse);
            return;
        }

        // 3. 未登录，返回 401，前端跳转登录页
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"code\":401,\"msg\":\"未登录\"}");
    }
}
```

**启动类上需要加 @ServletComponentScan 才能扫描到 Filter**

```java
@SpringBootApplication
@ServletComponentScan   // 扫描 @WebFilter 等 Servlet 组件
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

**技术要点**：
- `FilterChain.doFilter()` 决定请求是否放行；不调用则请求被拦截
- 白名单放行登录接口和静态资源，避免未登录用户无法进入登录页
- 校验逻辑放在 Filter 里统一处理，Controller 无需重复校验
- Spring 中还有更细粒度的 **Interceptor（拦截器）**，基于 AOP，可拿到具体的 HandlerMethod，适合做权限校验

### 2.7 三种方案对比与选型

| 方案         | 状态存放       | 分布式友好 | 安全性                     | 适用场景                                     |
| ------------ | -------------- | ---------- | -------------------------- | -------------------------------------------- |
| Cookie 单用  | 客户端         | 是         | 低（明文，易篡改）         | 存非敏感偏好数据，配合 Session 使用          |
| Cookie+Session | 服务端       | 否（需共享）| 较高（数据在服务端）       | 单体应用、传统服务端渲染页面                 |
| JWT          | 无状态（客户端）| 是         | 较高（签名防篡改）         | 前后端分离、微服务、移动端                   |

**选型思考**：
- 单体项目、页面由服务端渲染：**Session** 简单直接
- 前后端分离、接口被多个客户端（Web/App）调用：**JWT** 更合适，无状态、易扩展
- 纯 Cookie 不适合做登录态，数据明文可见且有 CSRF 风险

## 四、问题与解决方案

### 4.1 登录接口没有走过滤器，但其它接口拦截生效了

**问题**：Filter 拦截所有请求，登录接口也被拦截，导致永远无法登录。

**解决**：把登录接口 `/login` 和静态资源（`/css/**`、`/js/**`、`/img/**`）加入**白名单**直接放行，其它接口才做登录校验。同时确认启动类加了 `@ServletComponentScan`，Filter 才能被扫描注册。

### 4.2 登录成功，但刷新页面后登录态丢失

**问题**：使用 Session 时，浏览器关闭后 SessionId 对应的 Cookie 是会话级（未设置 Max-Age），重新打开浏览器就失效；使用 JWT 时，token 存内存变量，刷新页面就没了。

**解决**：Session 场景下可以给 `JSESSIONID` 设置较长有效期，或调整 Session 超时时间；JWT 场景下，前端把 token 存到 `localStorage`（持久化），而不是只存在内存变量里，并处理 token 过期后的重新登录。

### 4.3 前后端分离跨域请求，Cookie 无法携带

**问题**：前端部署在 A 域名、后端在 B 域名，跨域请求时浏览器默认不携带 Cookie，Session 方案下登录态失效。

**解决**：后端开启 CORS 时设置 `allowCredentials(true)` 并明确 `allowedOrigin`（不能是 `*`）；前端 `fetch` 请求加 `credentials: 'include'`。如果是纯接口项目，也可直接改用 **JWT** 方案，token 通过请求头传递，天然规避跨域携带 Cookie 的问题。

## 六、总结与思考

本周通过登录认证这个真实需求，把 Cookie、Session、JWT 三种会话技术串起来理解了。最初觉得三者是"三选一"的关系，实践后才发现它们是层层递进、各有定位的：**Cookie 解决"浏览器怎么存"，Session 解决"服务端怎么存"，JWT 解决"无状态怎么证明"**。写 Filter 时也体会到，登录校验这种横切逻辑放在过滤器统一处理，确实让 Controller 代码干净很多，同时也理解了它和 Spring 拦截器的区别——Filter 是 Servlet 规范层面的，Interceptor 是 Spring MVC 层面的，能拿到具体的 HandlerMethod，做细粒度权限控制更灵活。下一步打算结合 Spring Security 深入学习，把认证、授权、密码加密这些工程化细节补全。
