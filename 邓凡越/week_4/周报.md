## 二、核心学习内容

### 2.1 登录校验的完整流程

一个规范的登录校验，远不止"查一下密码对不对"，完整链路如下：

1. **参数校验**：用户名、密码非空，格式合法
2. **查询用户**：根据用户名从数据库查出用户记录
3. **密码校验**：用加密算法比对密码（绝不能存明文）
4. **登录成功处理**：防会话固定、签发会话 / JWT
5. **拦截校验**：Filter / Interceptor 统一校验每次请求的登录态

**① 参数校验**

```java
public class LoginParam {
    @NotBlank(message = "用户名不能为空")
    private String username;

    @NotBlank(message = "密码不能为空")
    @Length(min = 6, max = 20, message = "密码长度需在 6-20 位之间")
    private String password;
}
```

```java
@PostMapping("/login")
public Result login(@Validated @RequestBody LoginParam param) {
    // 参数不合法时，Spring 会抛出 MethodArgumentNotValidException，由全局异常处理器统一返回提示
    ...
}
```

**② 密码加密（BCrypt）**

实际项目中密码绝不能明文存储，也不能用可逆加密或简单 MD5。**BCrypt** 自带随机盐值，相同密码每次加密结果都不同，能有效抵御彩虹表攻击。

```java
@Configuration
public class SecurityConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();   // Spring Security 提供的 BCrypt 实现
    }
}
```

```java
@Service
public class UserService {
    @Autowired
    private PasswordEncoder passwordEncoder;

    // 注册：加密后存储
    public void register(String username, String rawPassword) {
        String encoded = passwordEncoder.encode(rawPassword);   // 加密，结果含盐值
        userMapper.insert(username, encoded);
    }

    // 登录：比对明文与密文
    public boolean checkPassword(String rawPassword, String encodedPassword) {
        return passwordEncoder.matches(rawPassword, encodedPassword);
    }
}
```

**③ 登录成功后的安全处理**

```java
@PostMapping("/login")
public Result login(@Validated @RequestBody LoginParam param, HttpSession session) {
    User user = userService.getByUsername(param.getUsername());
    if (user == null || !userService.checkPassword(param.getPassword(), user.getPassword())) {
        return Result.error("用户名或密码错误");
    }
    session.changeSessionId();              // 防止会话固定攻击：登录成功后更换 SessionId
    session.setAttribute("userId", user.getId());
    return Result.success("登录成功");
}
```

**关键点说明**：
- 登录成功/失败要**统一提示**，不要泄露"用户不存在"与"密码错误"的区别，避免被枚举用户名
- `changeSessionId()` 重新生成 SessionId，防止攻击者先把自己的 SessionId 塞给用户，用户登录后被劫持
- 参数校验用 `@Validated` + 校验注解，配合 `@RestControllerAdvice` 统一处理校验异常

### 2.2 会话技术：从单机到分布式

上周的 Session 是存在**单台服务器内存**里的，一旦应用部署多台机器（集群），问题就出现了：

> 用户第一次请求命中了服务器 A，Session 存在 A 上；第二次请求被负载均衡转发到服务器 B，B 上找不到这个 Session，登录态就丢了。

**三种解决思路**：

| 方案             | 原理                                     | 缺点                                   |
| ---------------- | ---------------------------------------- | -------------------------------------- |
| Session 同步     | 各节点之间广播复制 Session 数据          | 网络开销大，节点多了扛不住             |
| 粘性会话         | 负载均衡把同一用户的请求固定到同一台机器 | 某台机器宕机则该用户登录态全部丢失     |
| Redis 集中存储   | Session 数据统一存到 Redis，所有节点共享 | 需要额外引入 Redis，多一次网络访问     |

**Redis 集中管理 Session（Spring Session）**

```java
@Configuration
@EnableRedisHttpSession          // 让 Spring Session 接管 HttpSession，数据存到 Redis
public class SessionConfig {
}
```

```yaml
# application.yml
spring:
  redis:
    host: localhost
    port: 6379
  session:
    store-type: redis           # 指定 Session 存储方式为 Redis
    timeout: 30m                # Session 超时时间
```

启用后，业务代码**不需要任何改动**——`HttpSession` 的 API 完全不变，只是底层存储从内存换成了 Redis，集群部署下登录态天然共享。

**技术要点**：
- 引入 `spring-session-data-redis` 依赖 + `@EnableRedisHttpSession` 即可无缝切换
- Session 中存放的 Java 对象必须实现 `Serializable`，否则无法序列化进 Redis
- Redis 存储 Session 一般会设置过期时间，与 Session 超时保持一致，避免 Redis 内存堆积

### 2.3 JWT 完整认证流程

JWT 上周讲了结构和基本用法，本周把它的**完整认证链路**串起来：

1. **签发**：登录成功，用密钥 + 用户信息（claims）生成 token 返回前端
2. **携带**：前端把 token 存 `localStorage`，每次请求放 `Authorization: Bearer <token>` 请求头
3. **校验**：服务端解析签名，验证 token 合法且未过期，从中取出用户信息
4. **续签**：token 快过期时给前端发新 token，保证用户无感续期

**JWT 工具类（含续签逻辑）**

```java
public class JwtUtils {

    private static final String SECRET_KEY = "mySecretKey123456";
    private static final long EXPIRE_MS = 60 * 60 * 1000;        // 有效期 1 小时

    // 签发：把 userId、username 放入 claims
    public static String generateToken(Long userId, String username) {
        return Jwts.builder()
                .claim("userId", userId)
                .setSubject(username)
                .setIssuedAt(new Date())
                .setExpiration(new Date(System.currentTimeMillis() + EXPIRE_MS))
                .signWith(SignatureAlgorithm.HS256, SECRET_KEY)
                .compact();
    }

    // 校验：返回 claims，供后续取 userId/username
    public static Claims parseToken(String token) {
        return Jwts.parser()
                .setSigningKey(SECRET_KEY)
                .parseClaimsJws(token)
                .getBody();
    }

    // 续签：剩余有效期不足一半时，重新签发新 token
    public static String refreshIfNeeded(String token) {
        Claims claims = parseToken(token);
        long remainMs = claims.getExpiration().getTime() - System.currentTimeMillis();
        if (remainMs < EXPIRE_MS / 2) {
            return generateToken(claims.get("userId", Long.class), claims.getSubject());
        }
        return null;   // 无需续签
    }
}
```

**前端携带 token 的方式**

```javascript
// 登录成功后保存 token
localStorage.setItem("token", token);

// 每次请求在请求头带上 token
fetch("/api/user/info", {
  headers: { "Authorization": "Bearer " + localStorage.getItem("token") }
});
```

**安全注意点**：
- **密钥管理**：签名密钥绝不能硬编码在代码里，要放配置文件或环境变量，生产环境用足够长的随机密钥
- **Payload 不是加密**：只是 Base64 编码，能轻易解码，绝不能放密码等敏感信息
- **防重放**：JWT 被窃取后无法在服务端主动注销，有效期要设置合理；关键操作可结合刷新令牌 + 黑名单
- **过期时间**：太短体验差（频繁重新登录），太长风险高（被盗长期有效），一般 30 分钟到 2 小时

### 2.4 Filter 深入

Filter 上周用来做登录拦截，本周进一步理解它的完整机制。

**生命周期**：Filter 有三个阶段，由 Servlet 容器管理。

| 阶段      | 触发时机                 | 典型用途           |
| --------- | ------------------------ | ------------------ |
| `init`    | 服务器启动时调用一次     | 加载配置、初始化资源 |
| `doFilter`| 每个请求都会调用         | 拦截、过滤、放行    |
| `destroy` | 服务器关闭时调用一次     | 释放资源           |

**多个 Filter 的执行顺序**：一个请求会经过多个 Filter，形成**过滤器链**（FilterChain），用 `@Order` 控制先后，数字越小越先执行。

```java
@WebFilter(filterName = "encodingFilter", urlPatterns = "/*")
@Order(1)                       // 先执行：设置编码
public class EncodingFilter implements Filter {
    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        req.setCharacterEncoding("UTF-8");
        res.setContentType("text/html;charset=UTF-8");
        chain.doFilter(req, res);   // 放行，进入下一个 Filter 或 Servlet
    }
}

@WebFilter(filterName = "loginFilter", urlPatterns = "/*")
@Order(2)                       // 后执行：校验登录
public class LoginFilter implements Filter {
    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        // ... 登录校验逻辑 ...
        chain.doFilter(req, res);
    }
}
```

**关键点说明**：
- 每个 Filter 必须调用 `chain.doFilter()` 才能把请求放行给下一个节点；不调用就是拦截
- `@WebFilter` 是 Servlet 规范注解，需要启动类加 `@ServletComponentScan` 才能被扫描注册
- Filter 作用在 **Servlet 规范层面**，在 Spring MVC 之前执行，静态资源请求也会经过 Filter

### 2.5 Interceptor 拦截器

Interceptor 是 **Spring MVC 框架**提供的拦截器，作用在 `DispatcherServlet` 分发之后、进入 Controller 前后。相比 Filter，它能拿到具体的 **HandlerMethod**（即将执行的 Controller 方法），做权限校验更灵活。

**HandlerInterceptor 的三个方法**

```java
@Component
public class LoginInterceptor implements HandlerInterceptor {

    // 进入 Controller 之前执行，返回 false 则中断请求
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws Exception {
        // 1. 只拦截 Controller 方法（放行静态资源映射等）
        if (!(handler instanceof HandlerMethod)) {
            return true;
        }
        // 2. 从请求头取 token
        String token = request.getHeader("Authorization");
        if (token != null && token.startsWith("Bearer ")) {
            token = token.substring(7);
            try {
                Claims claims = JwtUtils.parseToken(token);
                // 3. 解析成功，把用户信息放进 request，供 Controller 使用
                request.setAttribute("userId", claims.get("userId", Long.class));
                request.setAttribute("username", claims.getSubject());
                return true;
            } catch (Exception e) {
                // token 无效或过期，走下方统一处理
            }
        }
        // 4. 未登录，返回 401
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"code\":401,\"msg\":\"未登录或登录已过期\"}");
        return false;
    }

    // Controller 执行后、视图渲染前调用
    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response, Object handler, ModelAndView modelAndView) {
        // 可对响应做统一处理
    }

    // 整个请求结束后调用（无论是否异常）
    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) {
        // 清理 ThreadLocal、记录日志等
    }
}
```

**注册拦截器（WebMvcConfigurer）**

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Autowired
    private LoginInterceptor loginInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loginInterceptor)
                .addPathPatterns("/**")                       // 拦截所有请求
                .excludePathPatterns("/login", "/register",   // 放行白名单
                        "/css/**", "/js/**", "/img/**");
    }
}
```

**技术要点**：
- 拦截路径用 `addPathPatterns` 指定，用 `excludePathPatterns` 排除白名单，比 Filter 里手写白名单判断更优雅
- `preHandle` 返回 `false` 直接中断请求，不再执行 Controller
- Interceptor 是 Spring 的 Bean，**可以直接 `@Autowired` 注入业务对象**，天然整合进 Spring 容器
- 请求处理完成后，`afterCompletion` 适合做 `ThreadLocal` 清理，防止内存泄漏

### 2.6 Filter 与 Interceptor 对比

| 对比项         | Filter                                         | Interceptor                                  |
| -------------- | ---------------------------------------------- | -------------------------------------------- |
| 所属规范       | Servlet 规范（Servlet 容器提供）               | Spring MVC 框架                              |
| 触发时机       | 请求进入容器后、Spring MVC 之前                | `DispatcherServlet` 分发后、进入 Controller 前后 |
| 作用范围       | 所有请求（含静态资源、其它 Servlet）           | 只拦截经过 DispatcherServlet 的请求          |
| 能否拿 HandlerMethod | 否                                         | 是（`handler` 参数就是即将执行的方法）       |
| 获取 Spring Bean | 需要特殊方式                                     | 本身就是 Spring Bean，可直接注入             |
| 执行顺序       | 先执行（在拦截器外层）                          | 后执行（在 Filter 内层）                     |
| 典型场景       | 编码、跨域 CORS、请求日志、通用安全             | 登录校验、权限校验、参数预处理、敏感词过滤   |

**完整执行链路**（同一个请求）：

```
请求
  └─ Filter.doFilter()                    // 1. 过滤器先执行
       └─ DispatcherServlet 分发
            └─ Interceptor.preHandle()    // 2. 拦截器前置
                 └─ Controller 方法        // 3. 执行业务
            └─ Interceptor.postHandle()   // 4. 拦截器后置（视图渲染前）
       └─ Interceptor.afterCompletion()   // 5. 请求结束（视图渲染后）
  └─ 响应返回
```

**选型思考**：
- 需要处理**静态资源、其它 Servlet、编码跨域**等容器级逻辑 → 用 **Filter**
- 需要拿到 **Controller 方法信息**、基于注解做细粒度权限控制 → 用 **Interceptor**
- 登录校验两种都能做：Spring 项目中更推荐 **Interceptor**，因为它能直接注入 Service、拿到 HandlerMethod；而 Filter 更贴近 Servlet 底层，适合通用性更强的横切逻辑

## 四、问题与解决方案

### 4.1 配置了 Interceptor，但登录接口也被拦截了

**问题**：加拦截器后，调用 `/login` 也返回 401，导致永远无法登录。

**解决**：拦截器 `addPathPatterns("/**")` 拦截所有请求，必须用 `excludePathPatterns("/login", "/register", "/css/**", "/js/**", "/img/**")` 把登录注册接口和静态资源排除出去。比在 Filter 里手写 `WHITE_LIST` 判断更声明式、更清晰。

### 4.2 JWT 过期后用户要反复重新登录，体验差

**问题**：token 有效期 1 小时，到期后 `parseToken` 抛异常，用户被迫重新登录。

**解决**：采用**滑动续签**——校验时如果剩余有效期不足一半，就签发一个新 token 返回给前端替换旧 token（见 2.3 的 `refreshIfNeeded`）。更复杂的方案是引入独立的 **refresh token**（有效期长），access token 过期后用它换新，refresh token 才需要走重新登录流程。

### 4.3 部署两台服务器后，登录态在不同节点间"串不进去"

**问题**：Session 存在单机内存，负载均衡把请求分到另一台服务器后登录态丢失。

**解决**：引入 Spring Session + Redis，把所有 Session 集中存到 Redis（见 2.2），业务代码零改动即可集群共享。对比了 Session 同步、粘性会话两种方案后，确认 Redis 集中存储是扩展性最好、最常用的做法。

### 4.4 Filter 拿不到 Controller 方法信息，权限校验难做

**问题**：想在拦截时判断"当前接口是否需要管理员权限"，Filter 里只能拿到 URL，拿不到对应的方法和注解。

**解决**：改用 **Interceptor**——`preHandle` 的 `handler` 参数就是 `HandlerMethod`，可以直接读取方法上的自定义注解（如 `@RequireAdmin`）做细粒度鉴权，还能直接注入 Service 查询权限。这也验证了"Filter 管容器级横切、Interceptor 管 MVC 级控制"的分工。
