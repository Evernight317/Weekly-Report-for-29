## 二、核心学习内容

### 2.1 什么是 AI Agent

**Agent（智能体）** 可以理解为：**让大模型在"思考-行动"循环中自主完成任务的系统**。它不只是"回答你的问题"，而是能根据目标自己决定下一步做什么。

一个 Agent 通常包含四个要素：

- **大模型（大脑）**：负责理解任务、做决策、生成文本
- **规划（Planning）**：把大目标拆解成可执行的小步骤
- **工具（Tools）**：模型自身能力边界之外的"手脚"——搜索、计算、调 API、查数据库
- **记忆（Memory）**：保存上下文、历史决策，跨轮次复用信息

**与普通对话 LLM 的区别**：

| 对比项     | 普通对话 LLM                        | AI Agent                            |
| ---------- | ----------------------------------- | ----------------------------------- |
| 交互方式   | 一问一答，单次生成                  | 观察 → 思考 → 行动 的循环           |
| 能力边界   | 只会生成文本，无法触达外部世界      | 通过工具获取实时信息、执行操作      |
| 任务形态   | 单步任务（写文案、翻译）            | 多步任务（订机票、写并运行代码）    |
| 可控性     | 依赖人不断给出指令                  | 自主决策，但需要约束防止失控        |

**Agent 的工作循环**：

```
观察 (Observation) → 思考 (Thought) → 行动 (Action) → 观察 → ...
```

模型看到任务后，先思考需要什么信息，调用工具获取，再基于新信息继续思考，直到任务完成。

### 2.2 ReAct 结构（Reasoning + Acting）

**ReAct**（Reasoning + Acting，推理 + 行动）是当前 Agent 最主流的推理结构之一。核心思想是：**把"推理"和"行动"交替进行**——模型先想一步（Thought），再做一步（Action），观察结果（Observation），再想下一步。

**为什么有效**：
- 把推理过程**显式化**：模型每一步在"想什么、做什么"都写在输出里，人可监督、可干预
- 用工具结果**校准思考**：模型不会凭空猜，而是基于真实数据推理，减少幻觉
- 类似人类"边想边做"：遇到新情况能及时调整，不用预先想好一切

**ReAct 的循环示意**：

```
用户：上海今天适不适合去迪士尼？
Thought: 我需要知道上海今天的天气。
Action: call get_weather("上海")
Observation: 上海 多云 24℃，微风
Thought: 天气不错，适合户外活动。
Answer: 适合！上海今天多云 24℃，很适合去迪士尼。
```

**Python 伪代码实现**

```python
def react_agent(user_question: str, max_steps: int = 8) -> str:
    """ReAct 循环：Thought -> Action -> Observation，直到模型给出最终答案"""
    messages = [{"role": "user", "content": user_question}]

    for step in range(max_steps):                     # 防止死循环，限制最大步数
        response = llm.chat(messages, tools=TOOLS)    # 让模型思考，并决定是否调用工具

        if response.tool_calls:                       # 模型要调用工具
            for call in response.tool_calls:
                result = execute_tool(call)           # 1. 执行工具
                messages.append({"role": "tool",
                                 "tool_call_id": call.id,
                                 "content": str(result)})   # 2. 把结果回填给模型
        else:
            return response.content                   # 模型给出最终答案，结束
    return "已超过最大步骤数，任务未完成"
```

**ReAct 提示词模板**（约束模型的输出格式）：

```text
你是一个能调用工具的助手。请严格按下面的格式思考并行动：

Thought: 你当前的思考（这一步我需要什么信息）
Action: 要调用的工具名
Action Input: 工具的输入参数（JSON 格式）

当拿到 Observation（工具返回结果）后继续思考，
如果已经可以回答用户，直接以如下格式输出最终答案：
Answer: 你的最终回答
```

### 2.3 Plan-and-Solve 结构

**Plan-and-Solve**（先规划、再求解）是另一种主流结构：模型先**制定完整计划**，把大任务拆成一串有序步骤，再**逐步执行**。

**流程示意**：

```
用户：帮我写一个 200 字的产品介绍文案
Plan:
  1. 明确产品的目标用户和核心卖点
  2. 起草开头一句吸引注意力
  3. 展开 2-3 个卖点的阐述
  4. 结尾给出行动号召
执行:
  第 1 步: 目标用户是年轻的上班族，核心卖点是省时、提效...
  第 2 步: 开头用痛点切入...
  ...逐步完成，最后汇总为完整文案
```

**与 ReAct 的区别**：

| 对比项     | ReAct                                   | Plan-and-Solve                       |
| ---------- | --------------------------------------- | ------------------------------------ |
| 决策时机   | 边想边做，每步根据最新结果调整         | 先规划后执行，计划先行               |
| 可调整性   | 高，能随时根据工具结果改变方向         | 低，计划制定后按步执行               |
| 适用任务   | 动态、信息不完全、需要逐步探索的任务   | 结构清晰、可预先拆解的固定任务       |
| token 开销 | 较高（每步都要思考）                   | 较低（规划一次，执行紧凑）           |
| 可控性     | 过程可监督、可干预                     | 依赖计划质量，执行阶段较难干预       |

**选型直觉**：任务**动态多变**（不知道需要什么信息）→ 用 **ReAct**；任务**结构明确**（知道有哪些步骤）→ 用 **Plan-and-Solve** 更省 token 更高效。

### 2.4 工具调用（Tool Calling / Function Calling）

**为什么需要工具**：大模型本质上只会"生成文本"，它不知道今天的天气、搜不了实时新闻、算不了精确的算术、改不了数据库。工具调用让模型可以把动作"外包"给真实系统。

**原理三步**：

1. **定义工具**：把每个工具的"说明书"（名称、参数、描述）用 JSON Schema 告诉模型
2. **模型决策**：模型根据任务判断需要哪个工具，返回"工具名 + 参数"（而不是模型自己生成文本）
3. **执行并回填**：程序执行工具，把真实结果回传给模型，模型基于结果继续回答

**定义工具（JSON Schema）**

```python
# 给模型看的"工具说明书"
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的天气情况",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名，如：上海"}
                },
                "required": ["city"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "calculate",
            "description": "执行数学计算",
            "parameters": {
                "type": "object",
                "properties": {
                    "expression": {"type": "string", "description": "数学表达式，如：3*8+4"}
                },
                "required": ["expression"]
            }
        }
    }
]
```

**执行工具的循环**（在 2.2 的 `agent_loop` 中用到）

```python
def execute_tool(call):
    """根据模型要调用的工具，分发到真实实现"""
    name = call.function.name
    args = json.loads(call.function.arguments)   # 解析模型返回的参数
    if name == "get_weather":
        return weather_service.query(args["city"])   # 调用真实天气接口
    if name == "calculate":
        return eval(args["expression"])              # 执行计算
    return "未知工具"
```

**常用工具类型**：天气查询、网页搜索、计算器、数据库查询、调用第三方 API、文件读写。

**注意点**：
- **参数校验**：模型给的参数可能不合法（城市名写错），执行前要校验、给默认值、捕获异常
- **错误处理**：工具调用失败要返回"错误原因"给模型，让它换一种方式重试，而不是直接崩溃
- **防死循环**：工具可能被反复调用，必须设置**最大迭代次数**（如 8 次），超限强制结束

### 2.5 提示词编写（Prompt Engineering）

提示词是"给模型的说明书"，直接决定 Agent 表现的上限。本周总结了几个核心原则。

**基本原则**：
- **角色设定**：开头告诉模型"你是谁、做什么"，如"你是一个乐于助人的客服助手"
- **指令明确**：具体、无歧义，"用 3 句话总结"好于"简要总结一下"
- **给示例（few-shot）**：给 1-2 个输入输出例子，模型能模仿格式和风格
- **约束输出格式**：要求输出 JSON、表格或指定结构，便于程序解析

**结构化提示词模板**：

```text
【角色】你是一个专业的 Python 技术助手。
【任务】回答用户的编程问题，并给出可运行的示例代码。
【约束】
  - 代码使用 Python 3，包含必要的 import
  - 只回答与编程相关的问题
  - 回答控制在 200 字以内
【输出格式】
  1. 结论
  2. 示例代码（```python 代码块）
```

**Agent 场景下的系统提示词**：除了回答任务，还要约定"行为边界"——**何时用工具、如何思考、何时收尾**。

```text
你是订单查询助手，可以调用订单查询工具。
行为准则：
1. 用户问订单信息时，先调用 get_order 工具，不要凭空编造。
2. 工具返回空结果时，明确告诉用户"未查询到订单"。
3. 已经给出明确答案后，直接结束，不要继续调用工具。
```

**好与坏的提示词对比**：

| 差的提示词                         | 好的提示词                                   |
| ---------------------------------- | -------------------------------------------- |
| "帮我优化这段代码"                 | "帮我优化这段代码：性能优先，给出修改前后的对比，并说明每处改动的原因" |
| "介绍一下你自己"                   | "你是电商客服，用亲切友好的语气在 50 字内介绍自己，并主动询问用户需求" |
| "查询订单状态"                     | "查询订单号 2026081001 的状态；若订单不存在，回复'未查询到该订单'并引导用户核对订单号" |

**核心技巧**：好的提示词 = **明确的角色 + 具体的指令 + 约束条件 + 期望的输出格式 + 必要的示例**。

### 2.6 ReAct 与 Plan-and-Solve 的选型与结合

两种结构不是"二选一"，工程实践中经常**结合使用**：

- **任务简单、信息明确** → 直接 Plan-and-Solve：先出计划再执行，省 token
- **任务复杂、信息不全、需要探索** → ReAct：边做边调整
- **大型任务** → 先用 Plan-and-Solve 拆成子任务，每个子任务内部再用 ReAct 迭代执行（先规划框架，再逐步求解）

```text
用户：帮我做一个数据分析报告
Plan-and-Solve（框架）:
  Plan: 1.获取数据 → 2.清洗 → 3.分析 → 4.生成报告
  第 1 步进入 ReAct：
    Thought: 数据在数据库里，先查询。
    Action: query_database("SELECT * FROM sales")
    Observation: 返回 1000 行销售数据...
    Thought: 数据已获取，可以进入清洗步骤。
```

## 四、问题与解决方案

### 4.1 Agent 反复调用工具，陷入死循环

**问题**：Agent 不停调用同一个工具，永远不会给出最终答案，直到触发最大步数限制。

**解决**：三层防线——① 主循环设置**最大迭代次数**（如 8 次），超限强制结束并返回提示；② 系统提示词中明确"已给出明确答案后直接结束，不要继续调用工具"；③ 当模型连续多次调用相同工具且参数不变时，主动中断并提示模型"该工具结果已获取，请基于它回答"。

### 4.2 模型返回的工具参数解析失败

**问题**：让模型"输出 JSON 格式的工具参数"，偶尔输出格式不对，`json.loads` 直接报错，Agent 崩溃。

**解决**：改用**结构化的 Function Calling**——不在自由文本里要求模型输出 JSON，而是用 `tools` 参数声明工具，模型返回的就是结构化的 `tool_calls`，天然是合法 JSON，无需解析。同时把每个参数的 `description` 写清楚，降低模型出错概率；解析时加 try-except，失败就返回错误信息让模型重新组织参数。

### 4.3 工具返回结果太长太乱，模型看不懂

**问题**：数据库查询返回几十行原始数据，模型被淹没，答非所问。

**解决**：工具在返回前先**加工结果**——只回传模型需要的字段、截断超长内容、用文字做摘要（如"共查询到 5 条记录，总销售额 12000 元"），让回传给模型的 Observation 是"能直接读懂的结论"，而不是原始数据。

### 4.4 长任务用 ReAct 一步步思考，token 开销太大

**问题**：一个可以预先拆解的固定任务，ReAct 每步都"想一下"，消耗大量 token，耗时也长。

**解决**：换用 **Plan-and-Solve**——先让模型一次性生成完整计划，再紧凑执行，中间思考轮次大幅减少。对"先规划再执行"仍拿不准的子步骤，再对子任务单独用 ReAct 迭代。两种结构按任务特点混用，而不是一根筋用 ReAct。

## 六、总结与思考

本周最大的转变是从"给系统写代码"到"给模型写规则"。Agent 让我直观理解了为什么 LLM 需要"手脚"：模型再聪明，也只能在文本世界里思考，**工具调用本质上是把模型能力边界之外的活"外包"给真实系统**，而推理结构（ReAct / Plan-and-Solve）决定了这份"思考"是边做边想还是先想后做。写 ReAct 循环时遇到死循环、参数解析失败，也让我意识到 Agent 开发的核心难点其实不是"让模型聪明"，而是"**让模型可控**"——最大步数、工具 schema、系统提示词的约束，都是在给模型的自由度画边界。下周想继续深入 RAG 和记忆机制，把 Agent 从"能调工具"提升到"能利用知识库"。
