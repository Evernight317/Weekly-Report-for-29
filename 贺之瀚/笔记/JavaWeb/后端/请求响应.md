# 请求响应

## 访问流程

Tomcat是一个Servlet容器，DispatcherServlet前端控制器

请求(HttpServletRequest）：获取请求数据
响应（HttpServletResponse）：设置响应数据

B/S架构：Browser/Server，浏览器/服务器架构模式；客户端只需要浏览器，应用程序的逻辑和数据都存储在服务端。（只需要维护服务端，体验不如CS架构）

C/S架构：Client/Server，客户端/服务器架构模式；（开发维护麻烦，但是体验好）

## 一、请求

浏览器地址栏只能发起get请求；后端测试功能时，只能用地址栏访问，即只能测试get请求，无法测试post请求；

---

get请求传递参数的常见方式：查询参数、路径参数；查询现在就是`?...`，路径就是直接嵌在URL中

---

### 1.Postman

Postman是一款功能强大的网页调试与发送网页HTTP请求的Chrome插件；

常用于进行接口测试；

### 2.简单参数

#### 原始方式

在原始的web程序中，获取请求参数，需要通过HttpServletRequest对象手动获取；

#### SpringBoot方式

请求参数名与方法形参变量名相同，且会*自动进行类型转换* ；

没有获取到参数值就是null，参数对应不上，不报错；

但是如果参数值和形参名不同的话，要用`@RequestParam` 建立映射；该注解的`required` 属性默认是true，代表请求参数必须传递，不传递则报错，如果是false的话，不传递也不会报错，当然值就是null了；

### 3.实体参数

简单参数：前端声明的请求参数个数=后端接受方法的声明形参数量；当多个参数时，简单参数就比较复杂了，相当于一个方法有多个形参；

因此后端可以将接受的所有参数封装进一个**实体类** 中，这样通过实体对象就可以接受所有参数，减小了码量和复杂度；（重写toString方法后就可以通过输出对象输出所有参数）

**规则** ：请求参数名与形参对象属性名相同，即可直接通过POJO接收；（一般把封装的实体类名称为POJO）

### 4.数组集合参数

form表单有checkbox复选框选项，这个会向后端传递多个值，发送的话就把每个值分开发送即可（key要求相同），接受就选择数组/集合来接受；

**发送** ：请求参数名与形参数组名称相同且请求参数为多个，比如`?hobby=java&hobby=cs2&hobby=genshin`；

接受：定义数组/集合类型形参即可接收参数，*变量名与key保持一致* ；

#### 数组接收

请求参数名与形参中数组变量名**相同** ，可以直接使用数组封装；

#### 集合接收

请求参数名与形参中集合变量名相同，通过`@RequestParam`绑定参数关系

由于默认是数组形式接受，用集合接受的话要用`@RequestParam`建立映射绑定；

### 5.日期参数

形参前面加上`@DateTimeFormat` 注解完成日期参数格式转换；

### 6.JSON参数

**POJO** (Plain Old Java Object) 简单Java对象；

（JSON格式数据要用post，放在请求体中传递到后端）

JSON后端用对象接收；要求*JSON数据键名与形参对象属性名相同* ，定
定义POJO类型形参即可接收参数，形参前需要使用`@RequestBody` 标识

### 7.路径参数？？？不理解

参数同时也是URL的一部分，如`http://localhost:8080/path/100`，100既是参数也是路径的一部分；但这也带来一个问题，*URL是动态的* ，如果用@RequestMapping的话后面不能写确定的数字不然无法匹配URL，解决方法就是使用**占位符** ；

#### 单个路径参数

通过请求URL直接传递参数，使用`{}`来标识该路径参数，比如上面的path后面`path/{id}`，形参前使用`@PathVariable` 获取路径参数

#### 多个

比如`/{id}/{name}` ，每个形参前都要加上注解；

## 二、响应

### 1.@ResponseBody注解

`@ResponseBody` 是一个方法注解/类注解，在Controller方法/类上加注解；

作用：将方法返回值直接响应，如果返回值类型是实体对象/集合，将会转换为JSON格式响应；

`@RestController = @Controller + @ResponseBody` 因此一般见不到这个注解；

每一个方法都称为**功能接口** ；

### 2.统一响应结果

每个功能接口如果返回的值不同的话，前端接收响应数据会变得复杂，因此往往将响应结果封装在`Result`对象中，用一个统一的形式，方便解析；

`Result`对象中，提供了一些静态方法，能够快速创建Result对象，如`Result.success`

| Result成员       |                              |
| ---------------- | ---------------------------- |
| `Integer code` | 响应码，1代表成功，0代表失败 |
| `String msg`   | 提示信息                     |
| `Object data`  | 返回的数据                   |

```Java
@RequestMapping("/hello")
public Result hello() {
  	System.out.println("hello world");
  	return Result.success("Hello world");
}
```

## 三、分层解耦

### 三层结构

如果一个方法同时实现了多种功能的话，会对维护造成难度；最好的就是单一职责，即每个类

|            |                                                                                  |
| ---------- | -------------------------------------------------------------------------------- |
| controller | 控制层，接收前端发送的请求，对请求进行处理，并响应数据                           |
| service    | 业务逻辑层，处理具体的业务逻辑                                                   |
| dao        | 即Data Access Object，数据访问层（持久层），负责数据访问操作，包括数据的增删查改 |

浏览器发送请求，由Controller接受请求，并转发给Service，Service在处理数据前先访问Dao获取数据，获取后进行数据处理，并将结果返回给Controller，生成响应；

### 分层解耦

内聚：软件中各个功能模块内部的功能联系；

解耦：衡量软件中各个层/模块之间的依赖、关联的程度；

（耦合：一边代码动，另一边也要跟着动）

比如说是创建对象，如果切换了实现类，那另一边也要变，可以*把实现类的对象放在一个容器中，到容器中找对应的实现类* ，这样就完成了解耦

控制反转：Inversion Of Control，简称IOC；对象的创建控制权由程序自身转移到外部（容器），这种思想称为控制反转；容器中的对象称为bean对象；

依赖注入：Dependency Injection，简称DI；容器为应用程序提供运行时所依赖的资源，称之为依赖注入；

### IOC&DI入门

比如，Controller中要调用Service层的方法，Service要调用dao方法

1、将Service层及Dao层的实现类，交给IOC容器管理，即在Service和dao的实现类上方加上注解`@Component`；
2、为Controller及Service注入运行时，依赖的对象，即在Service和Controller调用相应其它层方法的上方加上`@Autowired`；

### Bean的声明

要把某个对象交给IOC容器管理，需要在对应的类上加上如下注解之一

|                 |                            | 位置                                            |
| --------------- | -------------------------- | ----------------------------------------------- |
| `@Component`  | 声明bean的基础注解         | 不属于以下三类时，用此注解                      |
| `@Controller` | `@Component`的衍生注解   | 标注在控制器类上                                |
| `@Service`    | `@Component`的衍生注解   | 标注在业务类上                                  |
| `@Repository` | `@Component` 的衍生注解 | 标注在数据访问类上（由于与mybatis整合，用的少)  |

- 声明bean的时候，可以通过value属性指定*bean的名字* ，如果没有指定，默认为*类名首字母小写* ，格式为`@Component(value = "BeanName")`或`@Component("BeanName")`；
- 使用以上四个注解都可以声明bean，但是在springboot集成web开发中，声明控制器bean只能用`@Controller`；

### Bean组件扫描

声明bean的四大注解后，要想生效，还需要被组件扫描注解`@Componentscan`扫描；

`@Componentscan`注解虽然没有显式配置，但是实际上已经包含在了启动类声明注解`@SpringBootApplication`中，默认扫描的范围是*启动类所在包及其子包* ；

解决方法有两种，第一种是在启动类上加上并覆盖默认注解为`@ComponentScan({"package1","package2"})`，但这种方法不推荐；第二种是按照SpringBoot规范将Controller、Service和dao等放在*启动类所在包及其子包* 下；

### 依赖注入注解

`@Autowired`注解意为自动装配，默认是按照**类型** 进行，即自动识别类型并装配至容器中，一个类型只能识别一个bean，如果存在多个相同类型的bean就会报错；解决方法如下

1、使用`@Primary`注解，用于在实现类上方标注，指定装配的优先级；

2、`@Autowired` +`@Qualifier("bean名")`注解，用于在`@Autowired`上方标注，指定装配的bean名（默认就是类名首字母小写）；

3、`@Resource(name = "bean名")`注解，这个属于jdk，用来*取代`@Autowired`注解* ，手动指定装配的bean；

@Resource 与@Autowired区别：

@Autowired是spring框架提供的注解，而@Resource是JDK提供的注解；

@Autowired默认是按照**类型** 注入，而@Resource默认是按照**名称** 注入；
